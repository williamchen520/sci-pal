## T-3 小修批（2026-10-25，未发版，7 项）

1. **排队期间取消不再白烧 docling**（`_parse_and_store` 的 `on_acquired`）
   回调改为**有返回值**：返回 `False` → 在 `ParserOrchestrator()` 构造**之前**
   抛 `ParseCancelled(stage="排队期间")`；返回 `None`/其它 → 照常解析（向后兼容，
   同步路由不传）。`ParseCancelled` 新增 `stage`，日志统一成
   `[INFO] 解析已取消（排队期间|解析后），未写库：<file>（<task_id>）`。
2. **守卫文件不再删除**（`sciPal_watchdog.launch_guard`）
   删掉 `finally` 里的 `unlink()` —— 那一步是「先放开锁、再动文件」，close 与 unlink
   之间有人抢到锁就能造出两个实例。守卫文件**允许常驻**，内容不参与任何判定；
   `--status` 改报三行：`存在=` / `held=`（LK_NBLCK 试抢即放）/ `data=`。
   （原「A5 正常退出后守卫文件不存在」作废，替代判据是「残留不影响」+ A7/A8 回归。）
3. **解析并发上限 3**（`PARSE_MAX_CONCURRENT` + `_parse_admit_lock`）
   `parse_async` 在 `create_task()` 之前做准入：`type='parse_paper' AND status='running'`
   达到 3 → **429** + `{error, running, limit}`，**不建任务行**。
   检查与建任务在同一把短锁里（与 `_parse_lock` 分开）。
   同步路由 `POST /api/papers/parse` **有意不做准入**（前端按钮是人点的），代码注释已写明。
4. **`tasks.params` 落库**：`create_task(task_type, params=None)`，`parse_async` 传
   `{"filename": ...}`；其余 4 个调用点不传，保持 NULL；`get_task()` 仍是 7 键。
5. **`complete_task` / `fail_task` 返回 bool**（`rowcount > 0`），调用方据此判断
   「状态迁移是否真的生效」。
6. **解析入口入参校验**：路径穿越 → 400；无后缀 → 404「不是普通文件」；
   有非 `.pdf` 后缀 → 400「只支持 .pdf」；`.pdf` 但不是普通文件 → 404。两个路由一致。
7. **`selftest` 不再硬编码论文**：从 `/api/papers/local` 动态选第一篇
   `parsed=True 且 paragraph_count>0` 的文件；一篇都没有时打印 `[SKIP]`，
   汇总单列 `SKIP: 1`（不计 PASS、不算 FAIL，`RESULT` 仍 PASS）。

**验证**：T3-1 a~e（排队取消 → 日志里**没有** `Starting parse pipeline for: _t1_b.pdf`，
对照组 A 的同一行**在**；`papers`/`paragraphs` 无 B；「排队期间」日志一条；解析期间取消仍走
「解析后」且不落库）；T3-3（连发 3 个 → 第 4 个 429 `running=3/limit=3`、任务行只 +3；
取消 1 个后可再提交；全部结束后 running=0）；T3-4（params 合法 JSON、GET 仍 7 键、
`generate_review` 的 params 仍 NULL）；T3-5（True/False/False 三条 + 接口层仍 completed）；
T3-6（4 条入参用例 × 两个路由，均不建任务行）；T3-7（动态选中、换文件仍 27/27、
无可用论文时 `SKIP:1 / PASS 26 / FAIL 0`）；T3-2（A7 三轮峰值 1 / 已拉起 1 / 守卫被占 1、

## T-4：单实例守卫 + 排队可观测（2026-10-25，未发版）

**背景**：T-2 把 `_parse_lock` 焊成「唯一一把锁」，前提是**一个进程**。验收时发现看门狗
能堆出两个 Flask 同时监听 5000（Windows `SO_REUSEADDR` 允许重复 bind，两个都能返回
health 200）—— 进程内锁被进程边界打穿。另一个问题：「排队中」那一行紧接就被
「解析中（docling）…」覆盖，排队完全不可观测。

**修改**（`scripts/sciPal_watchdog.py` + `api_server.py`）：

1. **拉起互斥守卫**（`logs/sciPal_launch.guard`）
   - 与 daemon 的 `sciPal_watchdog.lock` **分开**：前者只允许一个进程执行
     `launch + wait_until_ready`（短命），后者只允许一个 daemon 存活（长期）。
   - **用 OS 级文件锁**：`msvcrt.locking(fd, LK_NBLCK, 1)` 非阻塞抢
     `GUARD_LOCK_OFFSET=512` 那个字节，抢到就持有 fd 到拉起结束，`finally` close。
     进程被 `taskkill /F` → 锁随之释放，**不存在「stale 接管」这个概念**，
     也就没有「判活 → 删文件 → 重建」这段非原子操作。
   - 文件内容 `{pid,start,at}` 只供人看，**不参与判定**；打开用 `O_RDWR|O_CREAT`。
   - 锁**不能**放偏移 0：Windows 字节区间锁会连带挡住读被锁字节（实测
     `PermissionError`），而 A8 要求「持锁期间内容可读且逐字节不变」。
     内容固定占前 256 字节（空格补齐，`json.loads` 容忍尾部空白）。
   - `run_daemon()`：`launch + wait` 整段包进守卫，被占则本轮跳过。
   - `run_once()`：三道闸 ①已就绪 → ②有 daemon 在跑（拉起归它，`exit 0`）→
     ③端口已有人在监听（冷启动中，`exit 0`）→ 才进守卫拉起。
   - `--status` 报「锁是否被持有」（`LK_NBLCK` 试抢 + 立刻释放）+ `instance count`，
     不再做 pid 存活推断。
   - `launch()` 的 `return False` 改为 `return None`（签名 `int | None`，调用方判 `is None`）。

2. **排队可观测**（`_parse_and_store` 新增 `on_waiting` / `on_acquired`）
   - `on_waiting`：试抢锁失败（真要排队）时写「排队中」；
   - `on_acquired`：真正拿到锁时写「解析中（docling）…」；
   - 试抢点放在 **docling import 之后** —— 首次 import 要 10~15 秒，放在 import 之前
     会摸到一个「暂时空闲」的锁，漏报排队（实测冷启动下必现）。

**验证**：A1 两个 `--once` 同秒并发 → 60 s 内 29 次采样监听 PID 峰值 **1**，
日志恰好 1 条「已拉起」+ 1 条「守卫被占」；**A7**（stale 守卫 + 同秒两个 `--once`）
连做 3 轮，每轮峰值 1 / 已拉起 1 / 守卫被占 1 / 退出码 0,0 / 无守卫残留；
**A8** W1 持守卫期间起 W2 → W2 `exit 0`、不拉起、守卫内容逐字节不变；
A2 daemon 存活时 `--once` 不拉起且 `exit 0`；A5 正常退出后守卫文件不存在；
A6 `--status` 报「未持有」与 `instance count=1`（与 netstat 一致）。
B1 排队任务连续 10 次读到「排队中」（3 s 步伐 4 次）；B2 「解析中」只进入 1 次；
B3 排队期间取消 → `cancelled` 且无入库行；B4 单任务无「排队中」；
B5 `selftest` 27/27、`precheck` 0、数据回基线。

## 6-B 补丁：解析契约修正（2026-10-25，未发版）

**背景**：6-B 上线后发现 5 处契约不一致 —— 同一份 PDF 在三条代码路径给出两个答案、
锁只锁住一半、取消后仍然写库、`limit` 没有上限、目录缺失被伪装成「0 篇」。

**修改**（只动 `api_server.py` 与 `mcp_server/search_server.py`）：

1. **统一「哪条记录才算数」**（`_find_parsed_paper`）
   `papers.filename` 无唯一约束，同一 PDF 可能同时有 `paper_X_<hash>`（224 段）与
   `paper_X_<hash>_mineru`（0 段）。新增模块级 helper +
   `_PARSED_PAPER_ORDER = "ORDER BY total_paragraphs DESC, created_at ASC LIMIT 1"`，
   三处共用：同步 `/api/papers/parse`、异步快路径、`/api/papers/local` 的 parsed_map
   （后者由「后写覆盖」改为逐文件查询同一 helper）。
2. **锁下沉**（`_parse_and_store`）
   `_parse_lock` 原先只有异步路由占用，同步路由（前端「解析」按钮）裸跑 docling。
   现在解析 + 写库收敛到 `_parse_and_store()`，两个入口都只调它，锁在它内部
   `with _parse_lock:`；异步路由为显示「排队中」只做一次「非阻塞试抢 + 立刻归还」，
   **全仓库只有一处 `with _parse_lock`**。
3. **取消语义补全**（写库前第二次检查）
   `_parse_and_store` 新增 `before_store` 回调，在**解析完成后、写库之前**、锁内调用；
   异步路由回调查 `is_cancelled`，已取消 → 抛 `ParseCancelled` → **不写库**、
   任务保持 `cancelled`。docstring 如实写明「docling 期间无法中断，取消只在解析前 /
   写库前两个点生效」。
4. **`list_local_papers` 的 limit 硬钳**：`max(1, int(limit))` → `max(1, min(int(limit), 50))`，
   工具描述补「上限 50」。
5. **目录缺失不再伪装**：`data.error` 非空时返回
   `{"ok": false, "error": ..., "hint": ...}`，而不是 `total: 0`。
   Flask 侧 `/api/papers/local` **仍是 HTTP 200**（前端在用），只改 MCP 侧的呈现。

**验证**：三处（+MCP 第四处）对 `PMC12707946.pdf` 全部 `paragraph_count=224` / 同一 `paper_id`；
同步与异步同时发起时 docling 不重叠（异步 105.7 s ≈ 同步 55.1 s + 一次解析，
期间 `/api/health` 最大 0.35 s）；取消后盯 `papers` 113 s 计数恒为 565、无探针行；
`list_local_papers(limit=10000)` 返回 50 条且 `truncated=true`；目录缺失桩返回
`ok:false`；`selftest` 27/27、`precheck` 0、`running_task → running=false`。

**未动**：`papers` 表里 75 行 `_mineru` 空壳行（只统一读取口径，数据清理另议）。

## 修复：段落 FTS 触发器（2026-10-25，阻塞 6-B 真解析；未发版）

**背景**：`paragraphs` 表的**任何** INSERT / UPDATE / DELETE 都失败
（`table paragraphs_fts has no column named section_level1`）。**既有缺陷**，非 6-B 引入，
被 6-B 的真解析验收趟出来；同步 `/api/papers/parse`（前端「解析」按钮）、6-B 的
`parse_async`、`build_db/dedup_papers.py` 的去重 DELETE 三条路径同时挂。

**根因**：`build_db/build_fts.py` 历史上 `DROP TABLE paragraphs_fts` 后按 5 列重建
（`section_l1` / `section_l2`），但 SQLite 的 `DROP TABLE` **不连带删触发器** ——
库里 `paragraphs_ai/ad/au` 仍在写 `section_level1/2/3`。全仓库没有任何代码重建它们
（`run_db_migrations()` 只加列/建表），所以不会自愈。

**修改**：
- `build_db/build_fts.py`
  - 新增 `PARAGRAPHS_TRIGGER_NAMES` / `PARAGRAPHS_TRIGGER_DDL` /
    `rebuild_paragraphs_triggers()` —— 触发器 DDL 的**全仓库唯一真源**。
    删除/更新走 `para_id`（**不用 rowid**：`paragraphs_fts.rowid` 与 `paragraphs.rowid`
    对齐率仅 11246/50950 ≈ 22%，按 rowid 删会删错别人的行）。
  - 新增 `paragraphs_triggers_need_fix()` —— 判据是把触发器里
    `INSERT INTO paragraphs_fts(列清单)` 的目标列与 `PRAGMA table_info(paragraphs_fts)`
    比对。**不能**用 `"section_level1" in sql`：修复后的 DDL 里必然有
    `new.section_level1`（那是 `paragraphs` 的真实列、数据源），子串判断会永远判定
    需要修 → 每次启动都重建打日志，破坏幂等。
  - `build_fts(db_path=None)` + CLI `--db`；**重建 FTS 后一并重建触发器**（堵住复发路径）。
- `api_server.py`
  - `run_db_migrations()` 末尾接判据 + 重建（幂等：第二次启动不 DROP、不 CREATE、不打日志；
    失败打印但**不阻塞启动**）。
  - 启动对账日志措辞 `遗留 review 任务` → `遗留持久化任务`（6-B 起白名单含 `parse_paper`）。
  - `parse_async` 失败分支先把 `progress` 置「已失败」再 `fail_task`
    （原来会留下 `status=failed | progress=写入数据库…`）。

**验证**：副本三向自证（insert 成功 / MATCH 命中 / update 无重复 / delete 归零，前后计数 Δ0）；
副本上重跑 `build_fts --db` 25.46 s → 触发器仍正确且再 insert 成功；prod 单次真解析
`status=parsed` / 29 段 / FTS 29 行 / `MATCH` 命中，清理后回到基线（papers 565、
documents 77）；两次真实重启迁移行只出现 1 次；`selftest` 27/27、`precheck` exit 0。

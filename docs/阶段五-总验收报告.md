### 4.4 五-C C-2：综述生成异步化（首个业务代码改动）

| 判据 | 期望 | 实测 |
|---|---|---|
| 异步性 | 返回 < 10 s | `generate_async` **0.031 / 0.067 / 0.135 s** |
| 端到端 | 任务完成且正文非空 | `max_papers=2` → **70 s** completed，markdown 2395 字 / 3 条参考文献 / 12 句全部通过引用校验 |
| 任务期间可轮询 | `health` 不超时 | 全程 **0.027 ~ 0.045 s** |
| **并发不串台** | 两任务参数各自对得上 | 同时提交 `use_llm_verify=false`+narrative+en 与 `true`+systematic+zh，**各自回显自己那份参数** |
| 工具数 / 断言 | 16 / 23 | 16 / 23 PASS |
| 红线 | 无 schema 改动、冻结签名不动、同步路由字段不减 | 全部满足；同步 `review/generate` 只被 `with _review_generate_lock:` 包起来（纯缩进变化） |

**这里又推翻了自己一次**：五-B 记录的「异步会把 `/api/health` 饿到 21.8 s」是**错的**。
模型热之后同一任务 5~7 s 跑完、35 次 health 采样全在 0.006~0.039 s。
21.8 s 是 embedding/reranker **首次加载**（进程 1.47 GB → 2.94 GB）的一次性冷启动。
真正的阻塞源是 `app.run(threaded=False)` —— 单线程，一次同步重请求会让所有请求排队。

### 4.5 五-C C-3：问答 / 多跳接入（含一次性能大修）

| 判据 | 期望 | 实测 |
|---|---|---|
| **检索栈不再重复加载** | 耗时下降、RSS 不随次数增长 | 同参数 `max_hops=1`：**71.5 s → 1.71 / 1.23 / 1.23 s**（约 58×）；连续 4 次 RSS `3,462,168K → 3,466,100K`（**+3.9 MB**，不增长） |
| 冷启动仍慢 | 如实承认，靠异步兜住 | 首调仍 **109 s**（共享检索器加载），故异步端点必要，**不能因热态 1.2 s 就退回同步** |
| 异步端点 | < 10 s | `ask_async` **0.025 s** / `search_async` **0.036 s** |
| 结果结构 | 完整 | agentic 含 `hops` / `final_coverage`；QA `answer` 3706 字 + citations + validation |
| 工具数 / 断言 | 18 / 25 | 8 + 9 + 1 = 18；25 PASS |
| 冻结签名 | `services/search/` 一行不动 | 未改 |

**根因（值得记住）**：`UnifiedRetriever.__init__` 是**饿汉式**——构造即加载 HybridSearch / Reranker /
ContextExpander / GraphTraverser / AbstractSearch。而 `QAService` 自建了一份、
`/api/agentic/search` **每次请求都 `new AgenticSearcher(...)` 且不传 retriever**，
于是每次调用都在重建检索栈、重加载一遍模型。修法只是注入 `get_retriever()` 共享单例（`AgenticSearcher` 本就支持注入）。

### 4.6 验收期间暴露的运维缺陷：看门狗重复拉起（已修）

C-2 验收压测时撞出来的，**不是本阶段引入的**：

| | 修复前 | 修复后 |
|---|---|---|
| 单实例监听 | 最多 **8 个** python 同时 LISTENING 5000，约每 60~70 s 多一对 | 7 分钟破坏性测试**峰值 = 1** |
| 自愈耗时 | — | 约 **108 s**（等模型加载完，而不是急着再拉一个） |

根因三重叠加：① `LAUNCH_COOLDOWN=60s` < 实测冷启动 ~76 s；② `run_daemon()` 拉起后**不等就绪**
（`--once` 会等 180 s，daemon 不会）；③ Windows `SO_REUSEADDR` 允许多进程绑同端口 → 静默无兜底。
修法：`wait_until_ready()` 阻塞等就绪 + 拉起前判端口占用 + `--status` 自检；另修了 detached 子进程
cp1252 编码导致 banner emoji 抛 `UnicodeEncodeError` 的问题（显式 `PYTHONUTF8=1`）。

### 4.7 C-3 收尾：selftest 清理静默失败（已修）

原实现里 selftest 在 `scipal-search` 会话中调 `cancel_review_task`（该工具只在 `scipal-generate`），
必然 `Unknown tool`；而 `call_tool` 返回错误结果**不抛异常**，代码只打 `[INFO]` 就过去，两条断言照样 PASS
——测试自己发起了两个重任务、清理失败、留下后台任务，还报 PASS。
改为 HTTP `POST /api/review/cancel/<id>`（`ProxyHandler({})` 绕代理），结果分级
（200 成功 / 404 视为已结束 / 其它 `[WARN]` 并进汇总），收尾查 `running_task` 并打印遗留 task_id。

当前实测尾部：

```text

汇总
  server 数 3 / 断言总数 25 / PASS 25 / FAIL 0 / 清理失败 0 / leftover_tasks 0 / RESULT PASS
```

## 七、验收方法学（比结论更该被复用）

这些判据都是被现实打脸之后换来的，下次别再从零试错：

| ❌ 不可靠的判据 | ✅ 改用 | 为什么 |
|---|---|---|
| 问模型「你有几个 `mcp__` 工具」 | 进程层：有几个含 `mcp_` 的 `python.exe`、父进程是不是 DSH | 实测模型凭日志/快照拼出过期清单（报 6 个，实际子进程 0 个） |
| 「新工具出现了」 | **「旧名消失 + 旧进程 0」** | 只有后者能排除新旧并存 |
| 「`health` 200 就没事」 | **数监听 PID 个数** | 堆积到 8 个实例时 health 照样 200 |
| 「旧工具还能调 = 新配置挂载失败」 | 先判**旧配置仍在运行**（关窗口 ≠ 退出，Electron 进托盘） | 本机踩两次 |
| 「只测错误路径的断言」 | 错误路径 + **正路径**都测 | `cancel_review_task` 只测 404 时，实现整个删掉也 PASS |
| 「测试清理失败打个 INFO 就行」 | 分级 + 计入汇总（`清理失败` / `leftover_tasks`） | 静默失败会导致测试自己污染环境还报 PASS |
| 「改完文档让 agent 重写一遍」 | 改完 **grep 关键字**核验更正没被回退 | CodeBuddy 把已作废的 `plugin_manager` 路线整段写回过一次 |
| 交付报告里的「已提交」 | `git log origin/dev..HEAD` 自己看 | 五-B / C-3 各出现一次「改完没提交」 |

另外两条 **CodeBuddy 反复出的错**，派单时必须点名：
- **「改完不提交」**（3 次：五-B、C-3、C-3 收尾前）。派单要显式写「执行完必须提交，不许留在工作区」。
- **「计数把自检覆盖当挂载数」**（五-B 写成 17，实际 13）。派单要区分「挂载数」与「断言数」。

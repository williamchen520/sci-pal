## 0. 为什么是这三件事

阶段五把「通路」修好了，剩下的是**能力缺口**。按「用户能感知到什么」排序，而不是按代码美观度：

| 阶段 | 内容 | 用户能感知的变化 | 依赖 |
|---|---|---|---|
| **6-A** | 任务持久化（review 任务从内存 dict 迁到 SQLite `tasks` 表） | 重启 Flask 后，之前拿到的 `task_id` **不再 404**；综述/大纲/问答/多跳的结果能跨重启查到 | 无 |
| **6-B** | 论文入库链路挂 MCP（列本地 PDF + 解析） | 模型可以自己看「有哪些 PDF 没入库」并触发解析，不必回 Web UI 点 | 依赖 6-A（解析要异步，异步要用持久任务存储） |
| **6-C** | `scipal-guard` 独立 server（领域词表校验） | 结论能按领域词表核一遍，不只靠 LLM 自证 | **待定**：词表数据源需要用户决策 |

**顺序不能换**：6-B 的异步解析要用任务存储，先做 6-B 等于把异步写两遍（先用内存版、再迁库）。

## 1. 阶段六-A：任务持久化（**本轮派单**）

工单：`docs/工单-阶段六A-任务持久化.md`

- 现状：`services/review/task_manager.py` 是 148 行内存 dict，`Flask 重启即丢`。
- 后果一：DSH 里模型拿到 `task_id` 后，只要 Flask 重启过（看门狗拉起、代码更新），
  轮询就是 `404 Task not found`，模型会判定任务失败。
- 后果二：历史任务无法回溯，`/api/review/running_task` 在重启后永远是空。
- 目标：换成 SQLite `tasks` 表（**已存在，11 列，当前 0 行**），
  **保留 9 个方法签名与返回值语义**，调用方零改动（`api_server.py:24` 的 import 不变）。
- 风险点集中在三处：**响应字段名映射**（`type/progress_text` → `task_type/progress`）、
  **条件语义**（cancel/complete/fail 只在 `running` 时生效）、**启动对账**（僵尸 running 要收尸）。

## 2. 阶段六-B：论文入库链路（**6-A 验收后再出工单**）

已核过的事实（2026-10-25）：

| 项 | 实测 |
|---|---|
| `POST /api/papers/parse` | **收 JSON body 的 `filename`**（`api_server.py:1655`），不是 multipart —— 已做路径穿越校验，MCP **可以直接传文件名** |
| 同步还是异步 | **同步**：docling 解析 + 写库，一次调用内完成 |
| 耗时 | **未知**（本地 77 篇 PDF 全部已解析，`papers` 表 565 行 / 未解析 0 篇，无法实测）→ 必须按"可能 > 60 s"设计 |
| `GET /api/papers/local` | 扫描 documents 目录，返回 `{filename, parsed, paper_id, title, …}`，可直接做只读工具 |
| `/api/papers/import` | 真 multipart，**这个才传不了文件流** → 维持不做 |

所以 6-B 的形状基本定了：**只读工具**（列本地 PDF / 查解析状态）+ **异步解析**（新端点 + `task_id` 轮询，
复用 6-A 的持久化存储），工具加到 `scipal-search`（8 → 10，第 3 次破例，需要写理由）。

> ⚠️ 一个修正：`docs/DSH插件化-路线图.md` §2.4 原写「`/api/papers/parse` … `/api/papers/import` 是 multipart，
> MCP 传不了文件流」，把两件事混了 —— **multipart 的是 `import`，`parse` 只要文件名**。
> 已在本次一并改正。

## 3. 阶段六-C：`scipal-guard`（**待用户决策，暂不派单**）

卡在**词表从哪来**，不是卡在代码。三个候选：

| 方案 | 词表来源 | 代价 |
|---|---|---|
| C-1 | 从 `papers`/`abstracts` 的标题+关键词统计高频术语，生成初始词表 | 全自动，但噪音大，需要人工审 |
| C-2 | 用户提供领域词表文件（CSV/JSON） | 最准，但要用户维护 |
| C-3 | 用 MeSH / 现有 ontology 拉取 | 覆盖广，但要外网 + 映射成本 |

**在做决定之前不派单**：没有词表，这个 server 只能包一层 LLM 自检，等于重复 QA 已有的 `validation` 字段。
决策后我再出工单。

## 4. 派单纪律（沿用阶段五的教训）

1. **一次只派一个阶段**，验收通过才派下一个；工单里写明「本工单现在就执行，不是下一轮」。
2. 每个工单的「零、背景事实」都现查核实、带行号，CodeBuddy **直接采信不重复查仓库**。
3. 验收一律**自跑**：重启、kill、并发实测，不看交付报告自述；
   尤其「改完没提交」「计数口径错」「文档重写把更正写回去」这三类它反复犯的错。
4. 业务代码改动必须**逐条列出**改了什么、没改什么，写进验收报告。

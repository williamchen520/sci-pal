## 六、验收中发现的新问题（建议立刻开 T-5）

### F-1（P1）**单进程里「重活」会把同一个 Flask 的所有请求拖到分钟级**

实测证据（全部今天，同一台机器）：

| 现象 | 数据 |
|---|---|
| 连发 3 个 `generate_review`，提交延迟 | **41.3 s / 0.5 s / 198.6 s**（同一进程，前一个任务的后台线程在跑） |
| `selftest` 四次运行失败项 | 3 / 0 / 1 / 3 条，全是 `health >45s`、`list_saved_outlines >45s`、`generate_outline 27.2s` 这类 |
| 混合检索器的懒加载 | 日志里 `✅ 混合检索器：本地检索已加载 / 在线检索已加载 / Protocols.io…` 都发生在**请求线程**里 |
| 实例跑久后 | 161 线程 / 11.2 GB，0.75 MB 的 PDF 解析从 ~18 s 退化到 **~100 s**；新实例同尺寸 0.26 MB 只要 23 s |

**机制**：所有重活（模型加载、检索、生成）都在同一个进程里；取消只改 DB 状态、**不终止工作线程**，
于是「点过取消」的任务继续吃 CPU/GIL，后续任何请求（连 `/api/health`）都可能排到 45 s 之后。
`selftest` 的失败就是被自己前面那些调用拖死的 —— **它不是产品坏了，是自检把「慢」判成了「错」**。

**另一条副作用**：提交响应超时（MCP 侧 45 s）时，任务**已经在服务端创建**、客户端却没拿到 `task_id`
→ 永远不会被取消 → 孤儿 `running` 任务长期占着算力。我在验收时就撞到一个（`19f2aa18`，靠
`/api/review/running_task` 才发现）。

**建议 T-5 范围（先诊断再改，别直接上并发控制）**：
1. 给每个懒加载点打一行「加载耗时」（检索器 / 在线 / protocols / LLM），确认到底哪一步在请求线程里花了几十秒；
2. 把这些加载挪到**启动预热**里（已有预热钩子，扩到混合检索器的 online/protocols 组件）；
3. 服务端给「提交型」端点（`generate_async` / `outline` / `agentic` / `qa`）打一行提交耗时日志，便于下次定位；
4. 给「取消」加真正的停止信号：线程在每个阶段边界检查 `is_cancelled` 后 `return`（`generate_review` 已有
   阶段级检查，`generate_outline` / `agentic_search` 要补）；
5. 孤儿任务：启动对账已覆盖持久化类型，运行期再加一条「线程已退出但仍 running」的清理。
6. `selftest`：把「提交耗时」类断言与被测系统的「冷/热」状态解耦（首跑允许一次重试并记 `RETRY`），
   否则这套自检永远会报假失败。

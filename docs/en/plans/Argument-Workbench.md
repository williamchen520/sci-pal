# Work Plan: From "Review Generation" to an "Argument Workbench"

> Version: v0.1  
> Date: 2026-10-30  
> Applies to: SciPal V33.96+  
> Goal: Upgrade the existing "chapter-section-sentence-figure-table" document tree into auditable claim-evidence argumentation infrastructure.

---

## 1. Background and Assessment

### 1.1 Current State

SciPal already has:

- multi-user, workspace, project, experiment, run;
- hybrid retrieval (vector + FTS + RRF);
- bge embedding / reranker;
- evidence cards, citation validation;
- review outline and review generation;
- DeepSeek cloud LLM integration.

But "one-click review" still amounts to:

```text
topic → retrieval → outline → expansion → citations
```

What this chain produces is "text that looks like a paper", not "an argument that has been constrained by evidence".

### 1.2 Core Assessment

> A publication-grade paper is not "a long text jointly generated by multiple agents", but "a defensible claim + the evidence chain that supports it + the handling of counterexamples and boundaries".

So the next step should not be more optimization of "generate 5,000 words in one pass"; it should be building:

```text
document tree (evidence addresses)
    +
claim graph (argument relations)
    +
contradiction detection (counterexamples and heterogeneity)
    +
constrained generation (no evidence, no writing)
```

### 1.3 Why Now

The existing data already has the tree foundation:

| Object | Count |
|---|---:|
| papers | 3,308 |
| sections | 69,128 |
| paragraphs | 167,337 |
| sentences | 862,405 |
| figures | 13,471 |
| tables | 4,922 |
| citations | 182,817 |

Coverage:

- 3,075 / 3,308 papers have sections;
- 164,630 / 167,337 paragraphs have a `section_id`;
- 715,298 / 862,405 sentences have `char_start/char_end` (about 83%).

This means:

1. The tree is already usable, but not yet complete;
2. There is no need to rebuild parsing from scratch;
3. The tree should be connected to the claim layer rather than building another flat RAG.

## 2. Goals and Non-Goals

### 2.1 Goals

1. Establish the four-layer structure "document node → evidence unit → atomic claim → argument relation".
2. Every claim must be traceable back to:
   - paper;
   - section;
   - paragraph;
   - sentence / figure / table;
   - character offsets or bbox.
3. For every claim, support:
   - supporting evidence;
   - opposing evidence;
   - boundary conditions;
   - evidence quality;
   - current status.
4. Emit a contradiction report, but distinguish:
   - real contradictions;
   - apparent contradictions;
   - heterogeneity;
   - insufficient evidence.
5. Enforce during writing:
   - every paragraph binds to a claim;
   - every sentence binds to an evidence node;
   - sentences without evidence are not allowed into the body text.
6. Provide an evaluable benchmark and a human acceptance workflow.

### 2.2 Non-Goals

This stage does not do:

- fully automatic "one-click submission";
- automatic invention of research contributions;
- automatic replacement of peer review;
- a perfect claim graph for every paper;
- GraphRAG / multi-agent debate from day one;
- cloud by default for private data.

## 3. Design Principles

### P1: The tree is an address, not an argument

The tree answers:

```text
Where is this sentence?
```

The claim graph answers:

```text
What does this sentence support? What does it refute?
```

The two cannot substitute for each other.

### P2: Claims must carry qualifiers

A claim contains at least:

```text
population / intervention / comparator / outcome / unit / scope / time
```

A claim without qualifiers is not allowed into contradiction assessment.

### P3: Precise provenance is a first-class citizen

Every piece of evidence must satisfy:

```text
document_text[char_start:char_end] == evidence_text
```

Figure/table evidence must bind:

```text
paper_id + fig_id/table_id + caption + page/bbox
```

### P4: A contradiction is not "low text similarity"

Contradiction detection must distinguish:

- direct negation;
- numeric disagreement;
- different populations;
- different dose/intervention;
- different endpoints;
- causal vs. correlational;
- different time ranges;
- different definitions.

Many "contradictions" are in fact heterogeneity.

### P5: Humans decide at the key nodes

The following must be confirmed by a human:

- whether a claim is worth making;
- whether a contradiction is real;
- whether the evidence suffices to support the conclusion;
- whether to submit.

### P6: Narrow first, broad later

Start with claim anchoring and evidence relations inside a single paper;  
then cross-paper claim alignment;  
finally a whole-corpus argument graph.


## 6. Document Tree Changes

### 6.1 What Must Be Completed

1. Unify `node_id`:
   - `sentence:<sentence_id>`
   - `figure:<fig_id>`
   - `table:<table_id>`
2. Section paths:
   - `path` / `depth` exist, but completeness needs auditing;
   - fall back to `section_level1/2/3` when missing.
3. char offsets:
   - currently 83%;
   - for missing sentences, realign against the source text; sentences that cannot be aligned are marked `offset_missing`.
4. Figure/table reference relations:
   - build `figure_ref` / `table_ref`:
     ```text
     sentence_id → fig_id/table_id
     ```
   - parse "Fig. 3", "Table 2", "图 3", "表 2".
5. Cross-parent nodes:
   - a figure/table may be referenced by multiple sections;
   - do not force a single parent; allow a many-to-many `references`.
6. Parse quality:
   - add `parse_quality` to every node: `ok | partial | broken`;
   - nodes with errors must not enter the claim graph.

### 6.2 Degradation When the Tree Is Incomplete

If a paper is missing sections:

```text
paper → paragraph → sentence
```

is still usable, but:

- no "section-level" argument conclusions are allowed;
- claims are marked `structure_incomplete=true`.

## 7. Claim Extraction

### 7.1 Goal

Extract from sentences/paragraphs/figures/tables:

```text
atomic claim
```

Not a summary, not a topic sentence, not "this paper studies X".

### 7.2 Claim Types

At minimum:

```text
empirical      empirical result
causal         causal
mechanistic    mechanism
method         method/tool
comparative    comparison
policy         policy/application
definitional   definition
```

### 7.3 Extraction Input

Prefer:

```text
sentence + parent paragraph + containing section heading + figure/table caption
```

Do not feed isolated sentences alone.

### 7.4 Extraction Output

Strict JSON:

```json
{
  "claim_text": "...",
  "claim_type": "empirical",
  "qualifiers": {
    "population": "...",
    "intervention": "...",
    "comparator": "...",
    "outcome": "...",
    "unit": "...",
    "scope": "...",
    "time": "..."
  },
  "evidence_node": {
    "node_type": "sentence",
    "node_id": "...",
    "quote": "..."
  },
  "confidence": 0.0
}
```

### 7.5 Constraints

- `quote` must match the source text exactly;
- claims without an exact quote are discarded;
- uncertain claims are marked `needs_review`;
- no cross-sentence merging unless explicitly allowed.

## 8. Pro/Con Evidence Retrieval

### 8.1 Four Query Types per Claim

```text
support_query   evidence supporting the claim
refute_query    evidence opposing/weakening the claim
boundary_query  boundary conditions/exceptions
mechanism_query mechanistic explanation
```

### 8.2 Retrieval Scope

Chosen by claim type:

| Claim type | Priority sections | Evidence type |
|---|---|---|
| empirical | Results / Tables | numeric, statistical |
| causal | Results / Discussion | experiments, natural experiments |
| mechanistic | Results / Discussion | pathways, molecules |
| comparative | Results | controls |
| policy | Discussion / Review | policy analysis |

### 8.3 Ranking

Keep the existing:

```text
BM25 + dense + RRF + bge reranker
```

But add:

- structural filtering (section type);
- a separate route for figure/table evidence;
- refute queries must not be drowned out by supporting results.

### 8.4 Relation Determination

Candidate evidence goes into a classifier:

```text
supports / refutes / mentions / underdetermines
```

Requirements:

- provide a rationale;
- provide a quote;
- low-confidence items go to the human queue.

## 9. Contradiction Detection

### 9.1 Input

Two claims, both of which must have qualifiers.

### 9.2 Types

```text
direct_negation
numeric_disagreement
scope_mismatch
population_mismatch
method_difference
causal_vs_correlation
temporal_mismatch
definitional_mismatch
```

### 9.3 Flow

```text
1. Numeric/unit rule checks
2. NLI / scientific contradiction classifier
3. Structured LLM adjudication
4. Human review (high severity)
5. Write to contradictions
```

### 9.4 Output

Not "who is right and who is wrong", but:

```json
{
  "status": "apparent",
  "type": "population_mismatch",
  "reason": "the two studies enrolled different populations",
  "severity": "medium",
  "needs_human": true
}
```

### 9.5 Key Rules

- Contradictions may not be judged from vector similarity alone;
- Numeric comparisons must be unit-normalized;
- Different populations/doses/endpoints default to "heterogeneity", not "contradiction";
- Only direct negation, or a numeric conflict under identical conditions, is promoted to `confirmed`.

When generating each sentence:


### 20.1 Dual-Speed Architecture

The first two layers and the third layer should not advance at the same speed.

```text
Fast layer (mature, borrowed directly)
  retrieval → evidence → citations → QA → review draft

Slow layer (deliberate, human in the loop)
  claim → pro/con evidence → contradiction candidates → argument graph → writing gate
```

The fast layer optimizes for:

- recall;
- coverage;
- speed;
- traceability.

The slow layer optimizes for:

- precision;
- qualifiers;
- counterexamples;
- auditability;
- human adjudication.

The two layers are connected by the **claim ledger**.

Principle:

> The first two layers borrow the "mechanism", not the "one-click paper generation" goal;  
> the third layer does not start from a whole-corpus graph, but from a Claim Card.

## 21. Third-Layer Minimum Closed Loop: Claim Card and Toulmin

The third layer does not start from a "whole-corpus claim graph", but from a single **Claim Card**.

The graph is a result, not a starting point.

### 21.1 The Six Elements of a Claim Card

Using the Toulmin argument model:

| Element | Meaning | System field |
|---|---|---|
| Claim | the assertion | `canonical_text` |
| Grounds | supporting evidence | `claim_evidence` |
| Warrant | why the evidence entails the claim | `warrant` |
| Backing | methodological/theoretical support | `backing` |
| Qualifier | qualifiers | `qualifiers_json` |
| Rebuttal | counterexamples/exceptions | `rebuttal`, `strongest_counter` |

Most AI writing systems only have:

```text
Claim + Grounds
```

What is missing is **Warrant** and **Rebuttal**.

And those two are the dividing line between "literature summary" and "argument".

### 21.2 Minimal Claim Card

```text
Claim
Qualifiers
Supporting evidence
Opposing evidence
Warrant (how the evidence entails the claim)
Strongest counterexample
Current status
Human decision
```

An evidence list without a `warrant` may not be turned into a paragraph directly.

### 21.3 Evidence Sources

`claim_evidence.evidence_source_type` must support at least:

```text
literature_sentence
literature_figure
literature_table
own_experiment
own_run
own_dataset
expert_note
```

Literature evidence must bind:

```text
paper_id + node_type + node_id + quote + offsets
```

Experimental evidence must bind:

```text
workspace_id + experiment_id + run_id
```

## 22. Claim State Machine

Do not use "true/false".

```text
DRAFT
  ↓
INTERROGATING
  ↓
SUPPORTED / CONTESTED / UNDERDETERMINED
  ↓
HUMAN_REVIEW
  ↓
ACCEPTED / REVISED / REJECTED / RETIRED
```

Explanation:

- `SUPPORTED`: the current evidence suffices for writing, not "objective truth";
- `CONTESTED`: substantive counterexamples exist, but the claim is still worth discussing;
- `UNDERDETERMINED`: insufficient evidence, cannot be written;
- `RETIRED`: superseded by a stronger claim.

Key:

> `CONTESTED` is not a failure; it is where a paper is most worth writing.

State transitions must record:

```text
who / when / from / to / reason
```

## 23. Seven-Step Interrogation Protocol

Every claim must go through it.

### 23.1 Operationalization

```text
What exactly are you claiming?
```

Turn a vague claim into a testable proposition.

### 23.2 Qualifiers

```text
population / intervention / comparator / outcome / unit / time / scope
```

Without qualifiers, a claim is not allowed into contradiction assessment.

### 23.3 Supporting Evidence

```text
Which studies support it?
```

### 23.4 Opposing Evidence

```text
Which studies oppose it?
Which studies partially oppose it?
```

This step requires an independent retrieval; you cannot only look for support.

### 23.5 Steelman

```text
What is the strongest opposing explanation?
```

Do not look for a straw man; construct the strongest version of the other side.

### 23.6 Evidence Quality

Do not give just a single score; give dimensions:

```text
study design
sample size
directness
consistency
risk of bias
precision
```

### 23.7 What Would Change Your Mind?

```text
If what evidence appeared, should this claim be abandoned?
```

This question directly exposes the claim's weak points.

## 24. Counter-Evidence Retrieval Is a Hard Constraint

It is not "we recommend looking for counterexamples", but:

```text
A claim that has not completed opposing-evidence retrieval cannot move to ACCEPTED.
```

You must record:

```text
query terms
retrieval scope
time
hit count
screening criteria
why no counterexample was found
```

Because:

> Not finding a counterexample ≠ no counterexample exists.

The system must be able to distinguish:

- there is genuinely no counterexample;
- retrieval did not cover it;
- the counterexample was filtered out.

Suggested additional fields:

```text
opposition_search_status
opposition_search_log
coverage_note
```

## 25. Contradictions Yield Candidates, Not Verdicts

Output:

```text
apparent_conflict
type
reason
qualifiers
evidence
needs_human
```

Types at minimum:

```text
direct_negation
numeric_disagreement
population_mismatch
method_difference
causal_vs_correlation
temporal_mismatch
definitional_mismatch
```

The system may say:

> "These two claims differ in population and endpoint; they may not be a contradiction but heterogeneity."

But it may not say:

> "Claim A is wrong."

### 25.1 Numbers and Units

Numeric conflicts must first go through:

- unit normalization;
- dimensional checks;
- time-window alignment;
- statistic-type checks (mean/median/hazard ratio).

### 25.2 Human Adjudication

High-severity contradictions must enter the human queue:

```text
confirmed / not_contradiction / resolved_by_scope / unresolved
```

## 26. Writing Gate

Only `ACCEPTED` claims may enter the outline.

### 26.1 Paragraph Structure

```text
paragraph = one main claim
          + several supporting/opposing evidence items
          + one qualifier
```

### 26.2 Sentence Structure

```text
every assertion sentence → at least one evidence node
```

Citation-free sentences are allowed for:

- transitions;
- questions;
- definitions;
- method descriptions.

But not allowed:

```text
causal assertions without evidence
"significant" without evidence
"first" without evidence
"outperforms" without evidence
```

### 26.3 Generation Order

```text
outline → paragraph claim assignment → evidence selection → sentence generation → citation validation → red-team review
```

Not:

```text
outline → one-shot expansion
```

## 27. Experiment Records as Evidence: SciPal's Differentiation

PaperQA2 and Veritas only have literature evidence.

SciPal also has:

```text
projects
experiments
runs
revisions
signatures
```

So a claim can be supported at the same time by:

```text
literature evidence + a run from our own lab
```

For example:

```text
Claim: Drug X lowers endpoint Z in model Y.

Literature support: 3 papers
Literature opposing: 1 paper (different dose)
Our lab: run_123 (dose 10 mg/kg)
Conclusion: supported, but qualified to 10 mg/kg
```

This is closer to real research than pure literature RAG.

Requirements:

- run evidence must bind `experiment_id` / `run_id`;
- record `planned_json` / `actual_json`;
- record deviations;
- experimental evidence must not masquerade as literature evidence.

## 29. Four-Week Pilot and Success Criteria

### 29.1 Pilot Scope

```text
one research topic
20 papers
10 claims
```

### 29.2 Four-Week Schedule

| Week | Content | Output |
|---|---|---|
| Week 1 | Humans write 10 claims and build the cards | Claim Card |
| Week 2 | Supporting/opposing retrieval, human labeling | Evidence ledger |
| Week 3 | Contradiction candidates and adjudication | Contradiction report |
| Week 4 | Generate one section from ACCEPTED claims | Draft + expert blind review |

### 29.3 Success Criteria

Not "5,000 words generated".

But:

1. experts say the claims are clearer;
2. we found counterexamples they did not previously know about;
3. assertions without evidence were removed;
4. every conclusion is traceable;
5. the adjudication process is auditable.

If these five hold, the third layer holds.

## 30. What Not to Do

- Do not build a whole-corpus claim graph first;
- Do not give claims a "truth score";
- Do not judge novelty automatically;
- Do not replace humans with an automatic reviewer;
- Do not let evidence pairs without a warrant generate paragraphs directly;
- Do not call every difference a "contradiction";
- Do not turn the claim graph into a knowledge graph;
- Do not mistake "merging" for "normalization".

## 32. One Sentence

> The third layer is not "teaching AI to argue",  
> but "letting the argumentation process leave traces and letting humans interrogate it claim by claim".

> It is not automating "writing papers", but turning "the defense of a claim" into an auditable workflow.

> Finish the infrastructure first, then validate claims with the smallest possible pilot;  
> do not use "wrapping up" to delay claims, and do not reinvest in claims while the corpus and domain conventions are still unstable.

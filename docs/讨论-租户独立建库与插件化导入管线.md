# 讨论记录：租户独立建库与插件化导入管线

> 日期：2026-11-14  
> 状态：讨论稿，未定稿  
> 主题：租户大规模导入、格式自动分流、审查/建库/建索引、插件扩展  
> 关联：主库建库脚本、XML/PDF/HTML source store、CodeRAG、联邦视图

---

## 1. 讨论背景

目前主库建库走的是**后端解耦脚本**：

```text
build_db/build_database.py
build_db/...
scripts/build_sentence_tree.py
code_rag/ingest.py
```

优点是：

```text
可批处理
可重跑
可审计
不依赖前端
```

问题是：

```text
脚本直接读全局 DSN
没有统一 import session
没有格式分流层
没有租户上下文
没有插件注册/版本
前端和 DSH 无法直接发起可追踪的大规模导入
```

现在要讨论的是：

```text
租户能否像主库一样，独立完成：
  大规模导入
  自动识别 PDF / XML / Python / R
  自动分流
  解析
  审查
  建库
  建索引
  建 CodeRAG

同时：
  与主库物理隔离
  与 XML/PDF 库不合并
  通过联邦索引形成逻辑单一库
  以后可以增加更多解析/审查/入库插件
```

结论先说：

```text
可以。
但需要把“脚本建库”升级为“租户级导入管线服务”。
不是给脚本加 tenant 参数，而是引入 ImportSession + Router + Plugin Registry。
```

## 2. 共识

### 2.1 主库和租户共用管线代码，不共用数据

```text
同一套 parser / review / index 代码
不同 TenantContext
不同物理库
不同索引命名空间
```

### 2.2 租户内部也按来源分库

```text
tenant_acme
  xml_library
  pdf_library
  html_library
  code_library
```

不合并成一张 `paragraphs`。

### 2.3 联邦层只做逻辑单一库

```text
query scope = main | tenant:<id> | both
grouped results
no cross-source score merge
provenance preserved
```

### 2.4 前端/DSH 只发起任务，不直接写库

```text
frontend / DSH
  -> POST import session
  -> 上传/挂载 manifest
  -> 查询进度
  -> 人工审查
  -> 批准发布
```

真正写库的是 worker。

## 3. 目标管线

```text
ImportSession
  -> staging
  -> Detect
  -> Route
  -> Parse
  -> Normalize
  -> Review
  -> Build
  -> Index
  -> Publish
  -> Federation register
```

### 3.1 ImportSession

```text
import_id
tenant_id
library_id
source_kind
manifest_uri
mode          xml | pdf | html | code | auto
status        queued | running | review | publishing | done | failed
total_items
processed
failed
created_by
created_at
```

### 3.2 Staging

```text
原始文件先落 staging
不直接进 canonical
```

保存：

```text
content_hash
size
mime
extension
source_uri
uploaded_by
```

### 3.3 Detect

检测顺序：

```text
1. magic bytes
2. MIME
3. extension
4. 内容特征
5. 解析器探测
```

不要只看扩展名。

### 3.4 Route

按格式分流：

```text
PDF        -> docling / pdf parser -> pdf_library
JATS XML   -> jats parser           -> xml_library
HTML       -> html parser           -> html_library
Python     -> python code parser    -> code_library
R / Rmd    -> R parser / Rmd parser -> code_library
未知       -> quarantine
```

同一批可以混合：

```text
batch_001/
  paper1.pdf
  paper2.xml
  analysis.py
  figure.R
```

Router 输出多条独立 pipeline，而不是强行放同一库。

## 4. 格式识别规则

### 4.1 PDF

```text
magic: %PDF-
MIME: application/pdf
extension: .pdf
```

### 4.2 JATS XML

```text
root: <article>
属性: article-type
包含: <front> / <body> / <back>
```

注意：

```text
不是所有 XML 都是 JATS
```

非 JATS XML：

```text
quarantine
或交给通用 XML 插件
```

### 4.3 HTML

```text
<!doctype html>
<html>
meta citation_title / citation_doi
```

### 4.4 Python

```text
.py
AST 可解析
或 shebang python
```

### 4.5 R / Rmd

```text
.R
Rmd / qmd
YAML header
<- 赋值
library() / require()
```

### 4.6 歧义处理

```text
低置信度 -> 不自动入库
标记 needs_review
允许人工指定 parser
```

不能为了自动化把格式猜错后静默入库。

## 5. 插件化设计

目标：

```text
以后增加新的文本解析器
增加新的审查规则
增加新的入库目标
不修改 orchestrator
```

### 5.1 插件类型

```text
SourceDetector
ParserPlugin
ReviewPlugin
IndexPlugin
SinkPlugin
```

### 5.2 统一接口

```python
class ParserPlugin(Protocol):
    name: str
    version: str
    input_kinds: list[str]

    def detect(self, item: SourceItem) -> Detection: ...
    def parse(self, item: SourceItem, ctx: TenantContext) -> ParsedDocument: ...
    def health(self) -> Health: ...
```

### 5.3 插件元数据

```json
{
  "name": "jats",
  "version": "1.0.0",
  "kind": "parser",
  "input": ["xml"],
  "output": "paper_tree",
  "config_schema": {},
  "capabilities": ["sections", "references"]
}
```

### 5.4 插件注册

```text
plugins/
  parsers/
    jats/
    pdf/
    html/
    python/
    r/
  reviewers/
    structure/
    duplicate/
    section_boundary/
  sinks/
    postgres/
    code_rag/
```

orchestrator 只依赖 registry：

```text
plugin = registry.resolve(kind, format, version)
```

### 5.5 插件隔离

```text
插件不直接拿全局 DSN
只拿 TenantContext
不直接写 canonical
只返回 ParsedDocument / ReviewResult / IndexBatch
由 sink 统一写
```

### 5.6 插件版本

```text
parser_version
review_version
index_version
```

每次入库记录版本，便于重放和回滚。

## 6. 审查层

审查不是单一 LLM 判断，而是分层门禁：

```text
L0 结构校验
L1 质量规则
L2 重复/冲突
L3 人工抽样
L4 发布批准
```

### 自动审查示例

```text
标题非空
DOI 格式
段落数 > 0
section 路径非空
PDF 页数/bbox
XML sec-type
代码语言识别
重复 hash
```

### 人工审查

```text
待审队列
批准/拒绝/退回
审查意见
审查人
时间
```

审查结果单独存 annotation，不写 canonical。

### 7.1 建库

```text

  -> canonical tree
  -> source-specific native tables
  -> annotation
```

### 7.2 建索引

```text
paragraph embeddings
sentence FTS

```

```text
index_namespace = tenant:<id>:<library>
```

### 7.3 发布

```text
draft -> reviewed -> published
```

未发布不进入联邦查询。

## 10. 租户物理隔离

TenantContext

  library_id

## 12. 风险

```text
1. 格式误判导致错误入库
2. 插件无版本导致不可重放
3. 租户批量导入压垮主库/模型
4. 审查不充分导致脏数据发布
5. 每租户独立 DB 的迁移成本
6. 联邦查询 fanout 延迟
7. 代码插件执行不可信代码
```

### 对策

```text
低置信度隔离
插件版本化
租户配额/队列隔离
发布门禁
迁移编排
分组查询
代码只解析不执行
```

## 14. 未决问题

```text
1. 一个租户一个 DB，还是每 library 一个 DB？
2. 审查是默认自动发布，还是必须人工批准？
3. 插件是否允许第三方代码，还是只允许内置插件？
4. 同一 paper 的 XML/PDF 是否要在租户内做 DOI 级去重？
5. 大文件/大批量是否走对象存储，而不是 HTTP 上传？
6. CodeRAG 是否允许执行代码，还是只静态解析？
7. 联邦查询是否允许跨租户？
```

## 15. 一句话

```text
把主库的“脚本建库”升级为“租户级导入管线服务”：
  ImportSession 管批次
  Detector/Router 管格式
  Plugin Registry 管扩展
  Review 管质量
  Sink 管独立建库
  Federation 管逻辑单一库
```

这样租户可以拥有和主库一样的能力，同时保留物理隔离。

## 4. 为什么不能直接装主环境

```text
GraphRAG 要求 numpy~=2.4 / pandas~=3.0 / pydantic~=2.13
主环境已有 SciPal 的 numpy/pandas/pydantic 约束
直接装会污染 app 依赖
```

PaperQA2 虽然没有 GraphRAG 那么激进的版本约束，但会引入：

```text
fhlmi / fhaviary
tantivy
PDF 解析栈
LLM provider 配置
```

这也不应该进入生产 app 的 venv。

## 5. 与 SciFact 任务的适配问题

Phase C 是：

```text
SciFact abstracts
claim -> sentence evidence
retrieval-only
```

PaperQA2 原生是：

```text
PDF / full-text
agentic QA
answer + citation
```

GraphRAG 原生是：

```text
文档图索引
实体/关系抽取
community summary
全局/局部问答
```

直接比较会混淆三件事：

```text
检索单元不同
输入粒度不同（abstract vs full text）
任务不同（retrieval vs QA）
```

结论：

```text
不能把 PaperQA2/GraphRAG 的原生分数
直接和 F0/Dense 的 sentence Recall 比
```

必须做适配层：

```text
SciFact abstract -> 文档
claim -> query
evidence sentence -> 评测 gold
只评 retrieval / citation，不评生成风格
```

## 6. 成本

### PaperQA2

```text
每个 claim 多次 LLM 调用
agentic search + answer
50 claims 可以小样本
500 claims 成本明显
需要 LLM API 或本地大模型
```

### GraphRAG

```text
建图阶段就要对 5,183 abstracts 做实体/关系抽取
/ community summary
即使只用 300 claims，图索引仍是全语料成本
```

结论：

```text
GraphRAG 不适合当前“先验证检索假设”的阶段
PaperQA2 可做 50 claims 适配烟测
```

---

## 7. 决策

```text
现在不原生运行 PaperQA2 / GraphRAG
不把依赖装进主 venv
不改生产 app
```

如果要做系统层：

```text
1. 建独立 venv 或容器
2. 先 50 claims 适配
3. 固定 prompt / model / budget
4. 只评 retrieval/citation，或单独评 answer
5. 再决定是否扩到 300/501
```

## 8. 下一步建议

优先级：

```text
P0  Phase C 收口：F0/Dense 基线 + B 上下文层
P1  系统层小样本：PaperQA2 adapted，50 claims
P2  GraphRAG：只在有图索引预算时做
P3  A/D/E/GA：Gate 2 未过，不启动
```

在系统层之前，先接受：

```text
F0 / Dense: 检索基线
B: 生成上下文
C/S/C2/C3/rerank/hybrid: 不进入主线
```

# 分析：检索耗时上涨与 T-5 单进程瓶颈的关系

> 对象：`docs/诊断-T5-单进程并发瓶颈.md`（WorkBuddy，2026-10-25）
> 对照：本轮 D 盘真实运行的 9 次 workflow（run a – run i）
> 结论用途：判断"检索从 50s 涨到 215s"是并发问题还是规模问题，以及 T-5 的修法对工作流意味着什么

---

## 1. 先给结论

1. **215s 不是 T-5 说的 GIL 阻塞**。CLI 工作流本来就跑在独立进程里，不抢 API 的解释器；耗时上涨来自**索引规模**和**候选宽度**，两者都是我们自己这两轮改出来的。
2. **但 T-5 的 P0 会直接卡住"把工作流搬进 API"这条路**——一旦 `generate_review` 在 Flask 线程里跑重活，报告里的 102s health 停顿、取消不停、进程静默消失都会原样复现。
3. T-5 推荐的方案 A（重活出进程）**正是我们已经在走的形态**：runner 用 `run.json` 做状态、阶段边界做审批、CLI 独立进程执行。方向一致，不需要改架构，需要补三件事：常驻 worker、阶段内取消点、模型实例复用。
4. T-5 里与我们直接相关的两条量化结论：**冷启动 114s 在模型加载**、**`get_hybrid_retriever()` 又建了第二套 HybridSearch（+9.7s + 一份内存）**。前者解释"为什么第一次跑总是慢"，后者是我们能立刻省掉的。

---

## 2. 实测数据（本轮 9 次运行）

| run | 时间 | retrieve | draft | 语料/索引状态 |
|---|---|---|---|---|
| a | 00:00 | 50.7s | 40.0s | 565 篇 / 51k 向量 |
| b | 00:40 | 46.5s | 41.5s | 同上，查询收窄后 |
| c | 00:52 | 47.6s | 25.6s | 去重后 551 篇 |
| e | 02:2x | 50.5s | 39.2s | 2,154 篇 / 向量只恢复 51k（FTS 全量） |
| f | 07:39 | **214.7s** | 54.4s | 2,154 篇 / 153k 向量 |
| g | 08:0x | **235.1s** | 30.3s | + 相关性过滤（30 段候选） |
| h | 08:0x | 222.9s | 74.7s | + 标题级过滤（候选被砍） |
| i | 08:1x | 220.0s | 2.8s（退化） | 回退为正文级过滤 |

同一条 `retrieve` 代码，只因为**向量库从 51k 涨到 153k、候选从 15 段涨到 30 段**，耗时从 ~48s 变成 ~220s（4.5 倍）。这是规模效应，不是锁竞争：CLI 进程独占，期间 API 的 health 探测不受影响（本轮未观测到 API 阻塞）。

## 3. 与 T-5 各项证据的对应

| T-5 结论 | 对本项目的含义 | 是否已受影响 |
|---|---|---|
| 冷启动 ~120s，几乎全在模型加载（retriever 114s：chroma 58 + reranker 50 + 摘要 12.5） | **每次 CLI 运行都要付一次**；常驻 worker 可以摊掉 | 是（run a 之前首次运行明显更慢） |
| 单进程 GIL：24 核只用 1.4 核，light 请求被拖到 102s | 只在"工作流跑进 API 线程"时发生；CLI 形态下不影响 | 否（但迁移到 API 就会） |
| 取消只改 DB，线程继续干 7.7 分钟 | 我们的 runner 也只在**阶段边界**检查取消；retrieve 内部一次 220s 无法中断 | 是（同构缺陷） |
| 进程在重活期间静默消失（P0，无 Traceback） | 若在 API 内跑重活，任务会丢；我们的 runner 有 run.json 可恢复，但 API 内任务不行 | 潜在 |
| 实例跑久变重：11.5GB / 提交延迟 198s（docling +3.5GB/次） | 解析/导入若进 API 进程，同样会累积 | 否（目前都在 CLI） |
| `get_hybrid_retriever()` 第二套 HybridSearch（+9.7s） | 每次运行多付一份加载和内存 | 是，可修 |
| self-check 把"慢"判成"错" | 我们用 `PYTHONUTF8=1` 跑自检时也见过超时类失败 | 是（验收口径要改） |

## 4. 215s 的构成（按可优化顺序）

1. **HNSW 规模**：153k 向量 vs 51k，加载 + 查询都线性变差；
2. **候选宽度**：`top_paragraphs` 从 15 提到 30（为相关性过滤留余量），rerank 与 MMR 翻倍；
3. **重复加载**：`get_hybrid_retriever()` 建第二套嵌入模型（T-5 已量化 +9.7s）；
4. **冷启动**：进程级模型加载无法避免，除非常驻。

给出一个可验证的分解方法：在 runner 里加 `--profile`，分别记录 `retriever_init`（模型/chroma 加载）、`search`（召回）、`rerank`（精排）三段，跑 3 次取中位数。目前只能凭总时长推断，下一步应把这个数测出来再决定砍哪一段。

---

## 5. 对工作流设计的具体影响（与 T-5 方案 A 对齐）

我们的形态已经接近方案 A，但还差三点：

| 缺口 | 现状 | 改法 |
|---|---|---|
| **常驻 worker** | 每次 CLI 运行都冷启动，模型加载重复付 | 起一个 `worker` 进程池（1–2 个），从队列取 `job.json`，进程内复用 retriever；runner 只做编排 |
| **阶段内取消点** | 只在 stage 之间检查 `--resume`/取消 | retrieve 的候选循环、rerank 批次、LLM 分段处插 `should_cancel()`；与 T-5 的"阶段粒度太粗"同解 |
| **模型实例复用** | `get_hybrid_retriever()` 另建一套 | 统一走 `get_retriever()`，或让 hybrid 复用 retriever 的 embedding 实例（T-5 第 5 条） |

另外两条与 T-5 一致的工程约束：

- **API 进程不跑重活**：`/api/reviews` 这类只读接口留在 Flask；生成/解析/检索走 worker，状态写 SQLite（我们已有 `tasks`/`reviews`/`run.json`）。
- **验收口径**：把"超时"与"功能错误"分开统计（T-5 证据 F）。我们的 `self_check` 也应把超时类失败单列，否则会重演"把慢判成错"。

---

## 6. 建议优先级

1. **P1：常驻 worker + 模型复用**（直接消掉每次 100s+ 的冷启动，并把 retrieve 拉回 100s 内）；
2. **P1：retrieve 分段计时**（先测量再优化，避免继续凭感觉调 `top_paragraphs`）；
3. **P2：阶段内取消点**（与 T-5 的取消问题同解，改动集中在 runner 与 retrieve 循环）；
4. **P3：索引瘦身/分区**（若语料继续涨，按 paper 元数据先过滤再进 HNSW）；
5. **P4：把 `get_hybrid_retriever()` 的双实例合并**（一次性 10s 收益，改动小）。

### 6.1 P1 实施后的实测（2026-10-26）

`services/workflow/worker.py` 已落地：常驻进程 + `stages._build_retriever()` 缓存，同一进程内连续处理多个 job。

| 场景 | retrieve | draft |
|---|---|---|
| 独立进程冷启动（run f/g/i） | 215–235 s | 2.8–74.7 s |
| worker 第 1 个 job（冷，m1） | **135.7 s** | 33.0 s |
| worker 第 2 个 job（暖，m2，不同主题） | **2.6 s** | 45.6 s |
| worker 同主题第 2 个 job（j2，命中查询缓存） | 2.7 s | 2.0 s |

结论：**模型复用确实把首段成本从 ~220s 降到 ~136s，且后续 job 免掉加载**。2.6 s 这个数偏低，包含检索器内部的查询/结果缓存（日志 `📦 从硬盘加载了 60 条缓存`），不能当作纯检索耗时；下一步的分段计时要把缓存命中单独标出来。

### 6.2 分段计时结果（`--profile`）

给 `retrieve` 加了阶段计时（`retrieval_diagnostics.mark`），一次单章节运行：

| 阶段 | 优化前 | 优化后 |
|---|---|---|
| entity_boost（其中 NER 模型加载） | **86,925 ms（86,877 为 NER）** | **56 ms**（NER 0 ms） |
| vector_search（153k 向量 HNSW） | 16,231 ms | 17,140 ms |
| rerank（cross-encoder） | 2,464 ms | 2,744 ms |
| mmr_diversify | 357 ms | 363 ms |
| abstracts | 281 ms | 363 ms |
| parent_contexts | 72 ms | 116 ms |
| **retrieve 内部合计** | **106,560 ms** | **20,931 ms** |

结论：**真正的瓶颈不是向量检索，是 `extract_key_entities` 里 scispacy 模型（`en_ner_bionlp13cg_md`）的一次性加载 87 秒**。修复方式：先用正则提取基因/蛋白名，命中就不再加载 NER；并支持 `SCIPAL_DISABLE_NER=1` 强制关闭（agentic_search.py）。

残余冷启动 ~90s 仍在 retriever 构造（嵌入 + reranker + 摘要库模型），由常驻 worker 摊掉；`retrieve` 内部已从 107s 降到 21s。

### 6.3 取消点（P2）

新增 `services/workflow/cancel.py`：在 run 目录放 `CANCEL` 文件即取消。runner 在**每个阶段开始前**检查并置 `cancelled`；retrieve 阶段在**每个章节开始前**检查并抛 `CancelledError`。与 T-5 的「取消只改库、线程继续跑」相比，至少不再把新阶段/新章节跑下去；单章节内部的 20s 检索仍不可中断。

## 7. 附：本轮另一个未完成项

68 对 PDF/XML 重复论文**尚未清除**。三次尝试（v2–v5）都在 `DELETE FROM paragraphs ... WHERE paper_id IN (...)` 阶段超过 10 分钟未提交——怀疑 `paragraphs` 上的 FTS 触发器（`paragraphs_ad`）对每行删除都做一次 FTS 写，删除数千段时退化成慢路径。

建议下一次用维护窗口做：

```sql
DROP TRIGGER paragraphs_ai; DROP TRIGGER paragraphs_ad; DROP TRIGGER paragraphs_au;
DELETE FROM paragraphs WHERE paper_id IN (SELECT ...);
DELETE FROM papers ...;
-- 重建 FTS（build_db/build_fts.py 会重建触发器）
```

这样删除是纯 SQLite 行删除，预期秒级；随后 `build_fts.py` 重建索引与触发器。

## 8. 检索相关性第二轮（2026-10-26）

### 8.1 尝试：标题命中排序（保留召回）

候选论文按「标题命中查询词数 → 最佳段落分」排序，只在每章上限截断时决定谁留下（不做硬过滤，之前硬过滤把证据砍到 3 条）。

| 运行 | 候选论文 | 相关 | 证据条数 | 说明 |
|---|---|---|---|---|
| p6（排序前） | 10 | 3 | 3 | 上限截断按检索顺序 |
| p7（排序后） | 10 | 3 | 11 | 排序生效，但候选集没变 |

结论：**排序不是瓶颈**。p7 的相关论文仍只有 3 篇，因为另外几篇 sepsis 论文根本没进候选池——瓶颈在**召回**，不在排序。

### 8.2 下一轮的正确方向：论文标题召回通道

`papers_fts` 已经建好（标题/作者/期刊），但目前只被「论文检索」通道局部使用。可行方案：

1. 用查询词在 `papers_fts` 里检索标题命中的 paper_id（`MATCH 'TLR4 OR sepsis'`）；
2. 对这些论文，按段落正文与查询词的重合度取前 k 段，作为额外候选加入 `sec_paper_ids`；
3. 与段落召回做 RRF 融合，再走现有排序与上限。

这样直接把「标题就写着 TLR4/sepsis」的论文拉进候选，绕开段落级语义漂移。预计改动集中在 `search_and_assign_papers` 的召回阶段，可用现有 10 篇用例做 A/B。

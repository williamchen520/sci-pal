# Sci-Pal Data Layer Architecture V2
## （极简版：单解析器 + 通用索引）

---

## 🎯 核心设计原则

> **从"多解析器 + 坐标对齐" → 砍到 "单解析器 + 索引"**

| 砍掉的 | 留下的 |
|--------|--------|
| 多解析器协同 | 单解析器（Docling） |
| 像素级坐标对齐 | ID编号匹配 |
| 800条人工规则 | 零规则，纯自动 |
| 交叉验证 | 不做，错了再说 |
| 复杂坐标系 | 一张通用索引表 |

---

## 📁 整体数据流（建库流程）

> **核心原则：先跑通主流程，再加可选子层。**

---

### 主流程（必做）：

```
PDF文件
  ↓
第一步：Docling 解析
  → 输出：元数据、段落、图片、表格、引用
  ↓
第二步：存主表
  ├─ papers表（元数据）
  ├─ paragraphs表（段落）
  ├─ figures表（图表）
  └─ citations表（引用）
  ↓
第三步：建段落级索引
  → index_table：段落↔图片、段落↔引用
  ↓
✅ 主流程完成！系统能用了！
```

---

### 可选子层（以后再加）：

```
主流程完成后，想更精细的时候：
  ↓
第四步：切句子（可选）
  → 遍历paragraphs表
  → 用正则按句号切句子
  → 存sentences表（sentence_id, paragraph_id, text, sequence）
  ↓
✅ 句子级精细查询可用了！
```

---

### 为什么要这个顺序？

1. **索引是核心，先建！** - 索引只需要paragraph_id，跟句子没关系
2. **句子是可选子层，后做！** - 不切句子，系统照样能用
3. **先跑通，再优化！** - 不要一开始就做完美，先能用再说

---

### Docling 能力说明：

| 能力 | Docling 原生？ | 我们怎么做？ |
|------|---------------|-------------|
| 拆段落 | ✅ 原生就有 | 直接用 |
| 提图表 | ✅ 原生就有 | 直接用 |
| 提引用 | ✅ 原生就有 | 直接用 |
| 拆句子级 | ❌ 没有这个功能 | 我们自己用正则切 |

**分工：Docling负责拆段落，我们自己负责拆句子。**

**ID命名规则**：`{paper_id}_para_{序号:03d}`

---

#### 📏 解析粒度设计决策：粗粒度索引 + 细粒度存储（重要！）

> **Docling 一步切到句子级，存储分两层，索引只建段落级。**

---

### 设计哲学：

| 层面 | 粒度 | 为什么 |
|------|------|--------|
| **索引层** | 段落级（粗） | 索引小、查询快、条数可控 |
| **存储层** | 段落+句子两级（细） | 细节全、随时能查、上下文完整 |

**一句话：粗粒度索引 + 细粒度存储，兼顾精确和上下文。**

---

### 完整流程：

#### 第一步：Docling 解析
- 输出：段落、句子、图片、表格、引用，**全切好**
- 句子带 `paragraph_id`，段落带 `section`、`subsection`

#### 第二步：分层存储

```
段落表（主）：paragraph_id, text, section, subsection
句子表（子）：sentence_id, paragraph_id, text, sequence
图片表：fig_id, file_path, caption, fig_number, section
引用表：ref_id, raw_text, doi, title, authors, year
```

#### 第三步：索引只建到段落级

```
索引表：
  source_id = paragraph_id
  target_id = fig_id / ref_id / table_id
```

**句子表不建索引，但通过 paragraph_id 随时能查。**

---

### 查询时怎么走？

```
用户查"图3"
    ↓
走索引表 → 拿到 paragraph_id
    ↓
用 paragraph_id 查段落表 → 拿到完整段落（上下文）
    ↓
用 paragraph_id 查句子表 → 拿到该段所有句子（细节）
    ↓
需要精确到某句 → 看 sentence_id / sequence
```

---

### 为什么这样设计最好？

| 好处 | 说明 |
|------|------|
| ✅ 索引小 | 只建段落级，条数可控，查询快 |
| ✅ 细节全 | 句子级数据存着，随时能查 |
| ✅ 上下文完整 | 段落是语义完整单元 |
| ✅ 精确到句 | 需要时，通过 paragraph_id + sequence 定位 |

---

**一句话：查关系走段落，抽细节走句子。**

### 表5：index_table（通用索引表）⭐ 核心！

> **一张表搞定所有关联！** 不用建N张关联表！

| 字段名 | 类型 | 说明 | 示例 |
|--------|------|------|------|
| `index_id` | INTEGER PRIMARY KEY | 自增ID | `1` |

| `source_type` | TEXT | 源对象类型 | `paragraph` / `figure` / `table` / `citation` / `paper` |
| `target_id` | TEXT | 目标对象ID | `paper_001_fig_3` |
| `target_type` | TEXT | 目标对象类型 | `paragraph` / `figure` / `table` / `citation` / `paper` |
| `relation_type` | TEXT | 关系类型 | `mentions` / `shows` / `cited_in` / `references` / `continues` |
| `paper_id` | TEXT | 所属论文（加速查询） | `paper_001` |

---

## 🔗 索引表都存哪些关系？

| 关系类型 | source | target | 说明 |
|---------|--------|--------|------|
| **mentions** | paragraph | figure | 段落里提到了"如图3所示" |
| **mentions** | paragraph | table | 段落里提到了"见表2" |
| **mentions** | paragraph | citation | 段落里引用了文献[7] |
| **shows** | figure | paragraph | 图3的图注在第042段 |
| **shows** | table | paragraph | 表2的表注在第058段 |
| **cited_in** | citation | paragraph | 文献[7]出现在第035段 |
| **references** | paper | citation | 论文引用了哪些文献 |
| **cross_refs** | citation | paper | 这篇引用的论文我们库里有没有 |

## 🔍 正反向查询怎么查？

### 正向查询：正文 → 图表

**用户在第040段，想看提到的图3**

```sql
SELECT target_id, target_type, relation_type
FROM index_table
WHERE source_id = 'paper_001_para_040'
  AND relation_type = 'mentions';
```

**结果**：`paper_001_fig_3` → 点一下就打开图3！

---

### 反向查询：图表 → 正文

**用户在看图3，想看上下文**

```sql
SELECT source_id, source_type, relation_type
FROM index_table
WHERE target_id = 'paper_001_fig_3'
  AND relation_type = 'mentions';
```

**结果**：`paper_001_para_040`, `paper_001_para_041` → 点一下就跳回原文！

---

### 跨篇查询：引用 → 被引论文

**论文A引用了Smith 2020，我们库里有没有这篇？**

```sql
SELECT cited_paper_id
FROM citations
WHERE doi = '10.1038/xxx';
```

**结果**：`paper_042` → 直接跳转到我们库里的这篇论文！

## 🕸️ 三层网络结构（设计核心思想）

> **文章内部 → 文章之间 → 领域之间，一层一层往上长！**

```
┌─────────────────────────────────────────────────┐
│  第三层：领域网络（更大）                         │
│  生物医学 ↔ 化学 ↔ 物理 ↔ ...                    │
│  （跨领域关联，L3+ 功能）                        │
└─────────────────────────────────────────────────┘
                        ↑
┌─────────────────────────────────────────────────┐
│  第二层：论文网络（中间层）                       │
│  论文A ↔ 论文B ↔ 论文C ↔ ...                    │
│  （通过引用、DOI、共同作者、共同关键词）           │
└─────────────────────────────────────────────────┘
                        ↑
┌─────────────────────────────────────────────────┐
│  第一层：论文内部网络（最小单元）                 │
│  段落 ↔ 图表 ↔ 表格 ↔ 引用                       │
│  （通过索引表关联）                              │
└─────────────────────────────────────────────────┘
```

---

### 为什么这样设计？

1. **每一层都是独立的**
   - 论文内部网络先跑通，再往上建论文网络，再往上建领域网络
   - 一层一层往上长，不用一开始就搞最复杂的

2. **每一层都能用**
   - 即使只有一篇论文，第一层也能用
   - 有100篇论文的时候，第二层就有价值了
   - 跨领域的时候，第三层就有价值了

3. **数据越多，网络越大**
   - 10篇 → 第一层够用
   - 100篇 → 第二层有价值
   - 1000篇 → 第三层有价值

---

### 现在我们在哪一层？

✅ **第一层：论文内部网络** - 现在在做！
   - 段落 ↔ 图表 ↔ 表格 ↔ 引用
   - 通用索引表

⏳ **第二层：论文网络** - 后面再做
   - 论文之间的引用关系
   - 共同关键词、共同作者
   - 按时间排序

⏳ **第三层：领域网络** - 更后面
   - 跨领域关联
   - 学科分类

---

## 📈 渐进式成长规律（重要！）

> **知识网络的价值，随节点数量呈指数级增长！**
> 
> 网络价值 V = N²（节点越多，价值越大）

---

### 为什么文献少了不行？

| 文献数量 | 能做什么？ | 为什么？ |
|---------|-----------|---------|
| **2-3篇** | 字段检索、并排对比 | 孤岛！连不成网 |
| **10-50篇** | 初步引用网、作者网 | 小领域脉络 |
| **100-500篇** | 完整网络、主题聚类 | 能写综述、做对比 |
| **1000+篇** | 路径推理、矛盾检测、空白发现 | 真正的"知识图谱" |

---

### 各阶段详细说明：

#### 📊 阶段1：2-3篇文献（起步期）
**能做什么？**
- ✅ 结构化检索
- ✅ 字段对比（并排展示）
- ❌ 没有网络效应
- ❌ 没有引用关系
- ❌ 没有共同作者

**为什么？**
- 两三篇论文互相引用的概率很低
- 同一个作者短时间内发两三篇相关论文的概率不高
- 两三个点，连不成簇
- 网络的价值 V = N²，N=3 时只有几条边

**系统怎么用？**
> 退化成"结构化检索 + 字段对比"
> 
> 用户搜"三阴性乳腺癌" → 系统从2-3篇里按标题/关键词匹配返回
> 
> 这已经比"读PDF"强了，只是"网络"的价值没发挥出来。

---

#### 📈 阶段2：10-50篇文献（成长期）
**能做什么？**
- ✅ 初步引用网：谁引了谁，形成链条
- ✅ 作者网：谁和谁合作，形成团队
- ✅ 主题聚类：关键词聚类，形成方向

**为什么？**
- 不需要"猜关系"，网络里已经有关系了
- 小领域的脉络开始清晰

---

#### 🚀 阶段3：100-500篇文献（成熟期）
**能做什么？**
- ✅ 完整网络：引用网、作者网、主题网都成型
- ✅ 主题聚类：自动找到研究热点
- ✅ 能写综述、做对比

**为什么？**
- 网络开始有价值了
- 能看到整个领域的全貌

---

#### 🧠 阶段4：1000+篇文献（智能期）
**能做什么？**
- ✅ 路径推理：A→B→C，发现间接关联
- ✅ 社区发现：自动聚类，找到研究热点
- ✅ 矛盾检测：两篇结论冲突，网络自动标出
- ✅ 空白发现：这个领域没人研究什么？

**为什么？**
- 你不需要"搜"，网络会"推"
- 真正的"知识图谱"

---

### 和词源项目的对比

| 词源项目 | 科研助手项目 | 共同规律 |
|---------|-------------|---------|
| 词库小的时候，关系也少 | 文献少的时候，网络也稀疏 | 数据量决定网络密度 |
| 词库大了，关系网才密 | 文献多了，网络才丰富 | 网络密度决定系统能力 |

**同一套逻辑！**

---

### 我们的策略

> **先把系统跑通，然后慢慢喂数据。喂得越多，它越聪明。**

1. **起步阶段**：先用10-50篇，跑通字段检索和对比
2. **成长阶段**：慢慢攒到100-500篇，网络开始有价值
3. **成熟阶段**：1000篇以上，网络开始"智能"

**不要指望两三篇就"网络智能"。那是数据库，不是知识图谱。**

## 🎯 为什么这样设计？

### 1. 为什么用单解析器（Docling）？
- ✅ 一个工具搞定所有，不用搞多解析器协同
- ✅ 输出格式统一，不用对齐坐标系
- ✅ 出了问题只查一个地方
- ✅ 以后想换解析器，换一个就行

### 2. 为什么用一张通用索引表？
- ✅ 不用建N张关联表（段落-图表表、段落-引用表、图表-段落表...）
- ✅ 加新关系类型不用改表结构
- ✅ 查询逻辑统一，写一次就行
- ✅ 索引好建，性能好调

### 3. 为什么砍了坐标对齐？
- ✅ 我们又不是做PDF阅读器，不需要像素级精确
- ✅ 用户要的是"大概在哪"，不是"精确到毫米"
- ✅ 页码 + 章节 + 段落ID，足够定位了
- ✅ 省了大量复杂的对齐代码

## 🧭 关于网络方向性的设计决策（重要！）

> **我们的网络是"关联网络"，不是"方向网络"。**

### 一、我们现在的网络是什么样？

现在的索引表，存的全是"关联"关系：
- 段落A → 图3：段落提到了图3
- 图3 → 段落A：图3被段落A提到
- 论文A → 论文B：论文A引用了论文B

**这些边，全是"对称"的，或者说是"可双向查"的。**

- 正反向索引，就是让你从两边都能查
- 但"谁指向谁"，在索引表里没有显式表达方向
- 你只能通过 source_type / target_type 大概判断，但不够硬

---

### 二、为什么方向性重要？

| 关系类型 | 方向的意义 |
|---------|-----------|
| **引用方向** | A引用B，和B引用A，意义完全不同。A引用B说明A受B影响，反过来不是。 |
| **时间方向** | A在B之前发表，A可能影响B，B不可能影响A。 |
| **因果方向** | 方法A导致结果B，不能反过来。 |
| **上下位方向** | 小鼠是哺乳动物的下位词，不能反过来说。 |

**没有方向，网络就是一张"无向图"：**
- ✅ 你能知道"谁和谁有关"
- ❌ 你不知道"谁影响谁"

---

### 三、怎么解决方向性问题？

#### 方案对比：

| 方案 | 怎么做 | 优点 | 缺点 | 我们选哪个？ |
|------|--------|------|------|-------------|
| **方案一** | 索引表加 direction 字段（forward/backward/symmetric） | 方向明确 | 多一个字段，多一条数据 | ❌ 不用 |
| **方案二** | 用 source/target 本身表达方向 | 简单，不用改表 | 方向隐含在 source/target 里 | ✅ **我们用这个！** |
| **方案三** | 加时间戳方向 | 跨篇方向天然明确 | 篇内没有时间先后 | ✅ 补充用 |

---

### 四、我们的最终方案

> **方向不是"存在网络里"的，是"查询时指定的"。**

#### 1. 篇内关系（段落 ↔ 图表）：无向，查询时定方向

```sql
-- 正向查：这段提到了哪些图？
SELECT target_id FROM index_table
WHERE source_id = 'paper_001_para_040'
  AND relation_type = 'mentions';
-- 结果：paper_001_fig_3

-- 反向查：图3被哪些段落提到？
SELECT source_id FROM index_table
WHERE target_id = 'paper_001_fig_3'
  AND relation_type = 'mentions';
-- 结果：paper_001_para_040, paper_001_para_041
```

**方向在哪？**
- 你查"这段提到了哪些图" → 方向是 段落→图
- 你查"图被哪些段落提到" → 方向是 图→段落（反向）
- **方向是你查询时自己定的，不是存在数据库里的！**

---

#### 2. 跨篇引用：有向，source/target 表达方向

```sql
-- 论文A引用了哪些论文？（正向）
SELECT cited_paper_id FROM citations
WHERE paper_id = 'paper_001';

-- 哪些论文引用了论文B？（反向）
SELECT paper_id FROM citations
WHERE cited_paper_id = 'paper_042';
```

**方向在哪？**
- source = 引用它的论文（paper_id）
- target = 被引用的论文（cited_paper_id）
- **方向已经在 source/target 里了！**

---

#### 3. 时间维度：天然方向，不可逆

这是我们网络里唯一"天然存在"的方向：

```sql
-- 按时间排序，找某篇论文之前的研究
SELECT * FROM papers
WHERE year < 2020
ORDER BY year DESC;
```

**为什么时间是天然方向？**
- 论文A发表于2020，论文B发表于2023
- A → B 的时间方向是固定的
- 不管你怎么查，A都在B之前
- **时间是不可逆的！**

---

### 五、和词源项目的对应

| 词源项目 | 科研助手项目 | 方向？ |
|---------|-------------|--------|
| 同义词 | 提到、引用 | ⭕ 对称的（无向） |
| 上下位词 | 时间先后 | ✅ 有方向的（有向） |

**一模一样的逻辑！**
- 对称关系 → 无向，查的时候定方向
- 层级关系 → 有向，方向天然存在

---

### 六、一句话总结

> **你的网络是"关联网络"，不是"方向网络"。**
> 
> 方向靠 source/target 表达，靠查询指定，靠时间戳兜底。
> 
> 这不是缺陷，是设计选择。

# 工作计划：插件端口与对比评测

> 日期：2026-10-31  
> 状态：计划，不含实现  
> 目标：让外部算法/工具以插件方式接入 SciPal 基座，在同一协议下做对比测试，并形成可发表的工程应用研究。

---

## 1. 背景与判断

### 1.1 问题

外部团队不断推出新的：

- 检索/重排算法；
- claim 验证 / NLI / CoE 方法；
- 论文生成 / 写作工具；
- 评测协议。

如果每接一个都改 `routes/`、`services/`、数据库和 UI，会产生三个问题：

1. 无法比较：每次集成的输入、输出、预算都不同；
2. 无法复现：没有记录插件版本、配置、数据快照；
3. 无法发表：只能写“我们接入了 X”，不能写“在统一协议下 X 优于 Y”。

### 1.2 判断

> 不是“加一个 API”，而是建立四件事：  
> **合同 + 注册 + 隔离 + 评测。**

端口由基座定义，插件只能实现合同，不能修改基座。

---

## 2. 目标与非目标

### 2.1 目标

```text
1. 定义稳定的插件端口合同
2. 建立 manifest / registry / loader
3. 建立统一的对比评测 harness
4. 记录 plugin run 的完整 provenance
5. 按 A → B → C 顺序落地三个端口
6. 产出工程应用类论文素材
```

### 2.2 非目标

```text
不做插件市场
不做动态 pip install
不执行不可信任意代码
不做一键论文
不修改 claim 状态作为插件副作用
不让插件直接读写 SQLite
```

---

## 3. 总体架构

```text
SciPal 基座
  ├─ Port 合同（core 所有）
  ├─ Plugin Registry（manifest 加载）
  ├─ Plugin Runner（隔离/超时/日志）
  └─ Evaluation Harness（统一对比）

plugins/
  ├─ manifests/
  │   ├─ claim-verifier-base.yaml
  │   ├─ retriever-bm25.yaml
  │   └─ paper-generator-base.yaml
  └─ adapters/
      ├─ claim_verifier_base.py
      ├─ retriever_bm25.py
      └─ paper_generator_base.py
```

### 3.1 四个核心对象

```text
PortContract   接口与 schema
PluginManifest 身份、版本、能力、资源、许可证
PluginRun      一次调用的输入/输出/耗时/成本
BenchmarkSpec  数据集、指标、预算、种子
```

### 3.2 运行记录

每次插件调用写 JSONL：

```json
{
  "run_id": "run_...",
  "plugin_id": "claim-verifier-base",
  "plugin_version": "0.1.0",
  "port": "claim_verifier",
  "dataset_hash": "sha256:...",
  "config": {},
  "seed": 42,
  "latency_ms": 1200,
  "cost_usd": 0.003,
  "output": {},
  "error": null
}
```

这是 **artifact-level provenance**，也是后续 CoE chain audit 的基础。

## 4. 阶段 A：ClaimVerifierPort

### 4.1 目标

在同一批 claim + evidence 上，对比不同 claim 验证方法：

- 现有 LLM NLI；
- 规则/关键词基线；
- 外部 NLI / CoE 工具。

### 4.2 合同

```python
class ClaimVerifierPort(Protocol):
    name: str
    version: str

    def verify(
        self,
        claim: ClaimInput,
        evidence: list[EvidenceInput],
        *,
        options: dict,
    ) -> ClaimVerification:
        ...
```

输入：

```json
{
  "claim_id": "claim_hcc_triple_os",
  "claim_text": "...",
  "qualifiers": {},
  "evidence": [
    {
      "evidence_id": "paper_..._sent_001",
      "quote": "...",
      "paper_id": "paper_...",
      "study_type": null,
      "endpoint": null
    }
  ]
}
```

输出：

```json
{
  "relation": "refutes",
  "confidence": 0.82,
  "rationale": "...",
  "evidence_ids": ["paper_..._sent_001"],
  "limitations": ["OS immature"],
  "plugin": {"id": "...", "version": "..."},
  "latency_ms": 1200
}
```

### 4.3 适配器

| 适配器 | 说明 |
|---|---|
| `claim-verifier-base` | 包装现有 `services/claims/nli.py` |
| `claim-verifier-rule` | 规则/方向词基线 |
| `claim-verifier-underdet` | 永远 `underdetermines` 的管线验证桩 |

### 4.4 数据集

```text
10 个 claim
32 篇 corpus
已有 5 条 underdetermines + 1 条 refutes
人工复核过的关系作为 gold
```

### 4.5 指标

```text
relation accuracy
macro-F1（supports/refutes/underdetermines）
refutes precision / recall
underdetermines recall
latency
cost
rationale 人工评分 1-5
```

### 4.6 验收

```text
1. 三个 adapter 走同一合同
2. 同一批 claim/evidence 可重复跑
3. 每次 run 写 JSONL
4. 不写 claim 状态、不写证据表
5. 输出对比表
6. 新增端口与 adapter 测试
7. 677 项 + 新增测试通过
```

### 4.7 风险

- 10 个 claim 太少，统计功效不足；
- LLM 输出不稳定，需要固定 seed/temperature；
- `refutes` gold 只有 1 条，recall 不可靠。

缓解：

```text
先做管线验证，不急于下“谁更好”的结论；
论文阶段再扩 claim 集。
```

## 5. 阶段 B：RetrieverPort

### 5.1 目标

在统一 corpus / query / top_k 下，对比：

- BM25；
- dense；
- hybrid RRF；
- hybrid + rerank；
- 外部检索算法。

### 5.2 合同

```python
class RetrieverPort(Protocol):
    name: str
    version: str

    def retrieve(
        self,
        query: str,
        *,
        corpus: list[str],
        top_k: int,
        options: dict,
    ) -> list[Candidate]:
        ...
```

输出：

```json
{
  "candidates": [
    {
      "paper_id": "...",
      "node_id": "...",
      "text": "...",
      "score": 0.82,
      "rank": 1
    }
  ]
}
```

### 5.3 适配器

| 适配器 | 说明 |
|---|---|
| `retriever-bm25` | 仅 FTS5/BM25 |
| `retriever-dense` | 仅 Chroma |
| `retriever-hybrid` | RRF |
| `retriever-hybrid-rerank` | 基座默认 |
| `retriever-external` | 外部检索器 |

### 5.4 数据集

```text
eval/gold/seed_100.jsonl
+ claim 派生查询
+ 32 篇 corpus 固定快照
```

### 5.5 指标

```text
Recall@10
MRR
nDCG@10
evidence coverage
latency
```

### 5.6 验收

```text
1. 同一 query 集、同一 corpus hash
2. 五个 adapter 输出同 schema
3. 对比表 + 失败案例分析
4. 不改变现有 `/api/retrieve` 行为
5. 测试通过
```

### 5.7 风险

- 不同检索器的候选粒度不同（段落 vs 句子）；
- 需要统一到 `node_id`；
- dense 检索依赖 Chroma 索引，必须固定快照。

## 6. 阶段 C：PaperGeneratorPort

### 6.1 目标

在 claim + evidence + writing brief 约束下，对比不同写作方法：

- 模板/确定性基线；
- 基座 LLM + writing brief；
- 外部论文生成工具。

### 6.2 合同

```python
class PaperGeneratorPort(Protocol):
    name: str
    version: str

    def generate(
        self,
        *,
        section_plan: dict,
        claims: list[ClaimInput],
        evidence: list[EvidenceInput],
        writing_brief: dict,
        options: dict,
    ) -> Draft:
        ...
```

输出：

```json
{
  "sentences": [
    {
      "text": "...",
      "claim_ids": ["..."],
      "evidence_ids": ["..."],
      "rhetorical_role": "assertion"
    }
  ]
}
```

硬约束：

```text
每个 assertion 句必须有 evidence_ids
must_not_write 不得出现
contested claim 必须写限定条件
```

### 6.3 适配器

| 适配器 | 说明 |
|---|---|
| `paper-generator-template` | 不调用 LLM 的确定性基线 |
| `paper-generator-base` | 基座 LLM + writing brief |
| `paper-generator-external` | 外部论文生成工具 |

### 6.4 数据集

```text
3 个 section plan
10 个 claim
32 篇 corpus
人工 rubric
```

### 6.5 指标

```text
sentence evidence coverage
unsupported claim rate
citation precision
forbidden phrase rate
human rating（论证质量/可读性）
latency / cost
```

### 6.6 验收

```text
1. 无 evidence_id 的 assertion 句被拦截
2. must_not_write 被拦截
3. 三个 adapter 同 schema
4. 人工盲评 2 人以上
5. 不自动写 claim 状态
6. 测试通过
```

### 6.7 风险

- 生成质量评测主观；
- 外部工具可能不可复现；
- 容易滑向“一键论文”。

缓解：

```text
只做 section-level，不做整篇；
先做写作闸门，再做生成对比。
```

## 8. 运行隔离与安全

### 8.1 最低要求

```text
插件不直接写 DB
插件不直接读全库
插件不直接拿 API key
插件不能无限运行
插件输出必须过 schema
```

### 8.2 推荐

```text
subprocess / container
  ↓
JSON-RPC 或 HTTP
  ↓
scoped input
  ↓
timeout + memory limit + network off
```

### 8.3 许可证

SciPal 是 AGPL-3.0-only。

插件接入前必须确认：

- 插件许可证；
- 是否允许商用；
- 是否通过网络分发；
- 是否构成衍生作品。

进程隔离可以降低耦合，但不能替代法律判断。

## 9. 论文计划

### 9.1 论文定位

不是“我们接入了几个工具”，而是：

> 一个可复现的插件化科研论证基座，以及在该基座上的 claim 验证 / 检索 / 写作方法对比。

### 9.2 贡献

```text
1. 端口化基座：合同、manifest、runner、provenance
2. 统一评测协议：同一数据/预算/指标
3. 三个端口的实证对比
4. 失败模式与适用边界
5. 可复现 artifact
```

### 9.3 实验表

| 端口 | 对比对象 | 主要指标 |
|---|---|---|
| ClaimVerifier | LLM / rule / external | macro-F1, refute recall |
| Retriever | BM25 / dense / hybrid / rerank | Recall@10, MRR, nDCG |
| PaperGenerator | template / base / external | evidence coverage, unsupported rate |

### 9.4 工程应用文章结构

```text
Introduction
Related Work
System Design
Port Contracts
Evaluation Protocol
Experiments
Error Analysis
Limitations
Reproducibility
```

### 9.5 不能声称的

```text
不能声称“我们的方法 SOTA”
除非有足够大的 benchmark 和统计检验
```

### 9.6 两个产出

```text
M4：Application Note 预印本（1500–4000 词）
```

#### A 阶段：平衡数据集（derived）

为解除标签不平衡，新增：

```text
scripts/build_claim_balanced_cases.py
eval/plugins/claims_pilot_balanced_cases.json
```

构造方式：

```text
10 个原始 claim
  × support（原始支持证据）
  × refute（显式否定 claim + 同一支持证据）
  × underdetermine（边界/方法句）
= 30 cases，10/10/10
```

结果：

```text
claim-verifier-rule           accuracy 0.4333
claim-verifier-underdetermines accuracy 0.3333
majority baseline             accuracy 0.3333
```

重要限制：

```text
refute 是 derived_opposite_claim，不是新的真实临床 claim；
underdetermine 复用 5 条边界证据；
发布前必须人工复核 derived refute 标签。
```

因此这 30 条可用于：

```text
端口对比、回归测试、方法筛选
```

不能用于：

```text
声称临床 claim 的 NLI 泛化性能
```

## 11. 每一步的停止条件

```text
A 阶段：
  如果 3 个 adapter 输出无法统一，停止，先修合同，不扩展 B。

B 阶段：
  如果 Recall@10 差异小于噪声，停止，不写“显著提升”。

C 阶段：
  如果 assertion 句无法稳定绑定 evidence，停止，先做写作闸门。

M4 阶段：
  如果关键指标没有可复现 run，停止写作，先补 run log / 数据快照。
```

## 13. Application Note 预印本计划

> 完成 M0–M3 后，优先写一篇 1500–4000 词的 Application Note 预印本，而不是直接写完整研究论文。

### 13.1 定位

Application Note 不是“完整研究论文”，它要回答：

```text
这个软件解决什么问题？
怎么用？
验证到什么程度？
在哪里获取？
限制是什么？
```

不要求：

```text
大规模多中心临床验证
SOTA 算法声明
完整理论创新
```

### 13.2 工作标题

```text
SciPal: an evidence-grounded, plugin-ready workbench for
claim-level literature interrogation
```

中文工作标题：

```text
SciPal：面向 claim 级文献审讯的证据驱动、可插拔工作台
```

### 13.3 目标形式

```text
类型：Application Note / Software Note
预印本：bioRxiv 或 arXiv（cs.DL / q-bio）
后续可投：Bioinformatics Application Note、
         BMC Bioinformatics、GigaScience、F1000Research
```

字数：

```text
正文 1500–4000 词
摘要 150–250 词
图 3–5 个
表 2–3 个
参考文献 30–50 条
```

> 具体上限以目标期刊为准；投稿前必须核对 Author Guidelines。

### 13.4 结构

```text
1. Motivation
   - 文献检索很强，但 claim 级论证很弱
   - 生成工具很多，但缺少可审计的证据链
   - 插件很多，但缺少统一对比基座

2. Software Design
   - L0–L4 数据层
   - 检索与证据信封
   - claim 审讯与人工裁决
   - writing brief
   - 插件端口

3. Key Capabilities
   - 结构化解析与句级溯源
   - 正反证据检索
   - claim 状态机与事件审计
   - 可插拔端口
   - 本地部署与多用户隔离

4. Validation
   - 677 项测试
   - 100 题 QA / SciFact / LitQA2
   - 10 个 HCC claim 的案例
   - claim_hcc_triple_os 的 OS 反证案例
   - 插件 A/B/C 对比（如果已完成）

5. Availability
   - GitHub / Gitee
   - AGPL-3.0-only
   - Docker Compose
   - 文档与示例数据
   - Zenodo DOI / release tag

6. Limitations
   - claim 集仍小
   - 在线 ingest 仍有限
   - 写作闸门仍是 brief + 人工检查
   - SQLite 单节点
```

### 13.5 必须准备的证据

写作前必须齐备：

```text
1. 一个冻结的 release tag
2. Docker 镜像 digest
3. 677 项测试输出
4. 100 题 QA 结果文件
5. SciFact / LitQA2 结果文件
6. claim 试点数据与裁决记录
7. 插件 A/B/C 对比结果（至少 A）
8. 关键截图 3–5 张
9. Zenodo / 机构仓库 DOI
10. 作者贡献与利益冲突声明
```

没有这些，不开始写。

### 13.6 不能写的内容

```text
不能写“首个”“唯一”“SOTA”
不能写“临床可用”
不能写“替代系统综述”
不能把 PFS 写成 OS
不能把“未找到反例”写成“已证明”
```

### 13.7 写作顺序

```text
1. 先定图与表
2. 再写 Results / Validation
3. 再写 Software Design
4. 再写 Motivation
5. 最后写 Abstract / Title
6. 统一术语与引用
7. 内部 red-team 审稿
8. 事实核查（每个数字有 run）
9. 预印本发布
```

### 13.8 时间安排

```text
第 1 周：图表 + 证据清单
第 2 周：初稿
第 3 周：内部评审 + 事实核查
第 4 周：润色 + 预印本发布
```

### 13.9 验收标准

```text
1. 正文 1500–4000 词
2. 每个性能数字有 run_id / 结果文件
3. 每个 claim 示例有 evidence_id
4. 所有图可复现
5. 代码与数据可用性声明完整
6. 许可证与第三方依赖合规
7. 通过内部 red-team
8. 预印本 DOI 可访问
```

### 13.10 风险

| 风险 | 缓解 |
|---|---|
| 被审稿人认为“只是工程集成” | 强调端口合同、评测协议、可复现性 |
| claim 集太小 | 明确定位为 case study，不声称泛化 |
| 生成质量主观 | 用 evidence coverage / unsupported rate + 人工盲评 |
| AGPL 许可疑问 | 明确许可证与依赖边界 |
| 预印本被 scoop | 先发布 preprint，保留版本记录 |

### 13.11 与完整论文的区别

| 维度 | Application Note | 完整论文 |
|---|---|---|
| 字数 | 1500–4000 | 6000+ |
| 重点 | 软件与可用性 | 方法与实证 |
| 实验 | 案例 + 小规模对比 | 大规模 + 统计检验 |
| 贡献 | 工具与协议 | 算法/理论/系统 |
| 风险 | 低 | 高 |

验收后再决定是否继续。

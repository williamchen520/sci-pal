## 七、发现问题（都不阻塞 T-2）

### F-1（P1，**新发现，环境级**）看门狗 `--once` 会堆出多实例 → 进程内锁失效

验收开场就撞到：`netstat` 显示 5000 端口 **两个 PID 同时 LISTENING**（`29396` WS 8263 MB / `1068` WS 1169 MB）。
父链显示两条都是 `api_server.py`，一条来自看门狗 **daemon**，一条来自 **`--once`**。

日志（`logs/sciPal_watchdog.log`）：

```
15:07:15 已拉起 api_server.py（pid=2300）
15:07:17 已拉起 api_server.py（pid=27880）   ← 2 s 后又拉了一个
14:57:28 已拉起（pid=8384）/ 同时 已拉起（pid=19968）   ← 同一秒两次
```

代码原因（`scripts/sciPal_watchdog.py`）：

- `run_daemon()` 有 F-3 端口守卫（`port_listening()` → 不重复拉起），并在失败时进冷却；
- **`run_once()` 既不看锁、也不走端口守卫**：`probe()` 失败就直接 `launch()`。
  于是「daemon 正在冷启动 + 有人跑一次 `--once`」必然双实例 —— 而 `_locked`/`F-1 等就绪`
  只保证单个 run 不重复拉，管不了两个 run 并行。
- 探针通过后两个实例都被判「已就绪」（Windows `SO_REUSEADDR` 允许重复 bind）。

后果不只是吃内存：**`_parse_lock` 是进程内锁，跨实例失效** —— T-2 刚修好的「双份 docling」在多实例下会原样回来。
我在验收中已收敛为单实例（当前 pid 27068，1 个监听），最后也顺势重启了一次把内存从 7.4 GB 收回到基线。

### F-2（P2）「排队中」进度被立刻覆盖 → 排队状态不可观测

见 §3。修法很轻：把「解析中（docling）…」的更新挪到**拿到锁之后**
（给 `_parse_and_store` 加一个 `on_acquired` 回调，在 `with _parse_lock:` 之内调用），
或者用 `if queued: 不再覆盖` 的写法。**别用「先 sleep 再判」这种试法。**

### F-3（P3 / 数据）单行且 `total_paragraphs` 未回填 → 仍会报 0 段

`PMC13612923.pdf` 只有 1 行：`paper_PMC13612923_2128aaf6_mineru`，`total_paragraphs=0`，
但 `paragraphs` 里该 `paper_id` 下有 **58** 段。统一取行口径只能「在多行里挑最好的」，
单行时无从挑。影响面：仅此 1 个 PDF（77 个里 1 个）；`paper_id` 是对的，只是段落数显示 0。

建议（数据修复，另议）：读取侧在 `total_paragraphs=0` 时回退 `COUNT(paragraphs)`，
或一次性回填这批 `_mineru` 行的 `total_paragraphs`。**改数据要单独点头。**

# 事故报告：测试建库误删主库表

> 日期：2026-11-10  
> 级别：P1 数据事故（开发阶段，无客户影响）  
> 状态：已止损，流程补丁待落地  
> 责任人：我（AI 代理）  
> 复盘原则：对事不对人，修系统而不是写检讨

---

## 1. 摘要

在为主库之外的 SciFact 评测建库时，我运行了一个未限定 schema 的：

```sql
DROP TABLE IF EXISTS paragraph_embeddings, sentences, paragraphs, papers CASCADE
```

脚本刚创建 `scifact_eval` schema，里面还没有这些表；PostgreSQL 按 `search_path` 解析到了 `public`，把主库的：

```text
public.papers
public.paragraphs
public.sentences
public.paragraph_embeddings
```

删除。

`/api/papers` 随后返回 503。

## 4. 根因

### 直接原因

```text
DROP TABLE 没有 schema 限定
依赖 search_path
```

### 深层原因

```text
1. 我在生产 DSN 上直接跑建库脚本
2. 脚本默认 search_path 包含 public
3. 没有 dry-run
4. 没有目标库/目标 schema 白名单
5. 没有 destructive SQL 审批
6. 没有“先备份再 DDL”的硬门槛
7. 没有在克隆库先演练
8. 单条 DROP 同时删四张表，爆炸半径过大
```

### 为什么没早点发现

```text
脚本执行前没有打印 current_database/current_schema
没有先 SELECT 目标表
DROP IF EXISTS 让“表不存在”看起来正常
搜索路径把“不存在”变成了“删 public”
```

## 6. 流程补丁

### 6.1 立即执行（硬规则）

```text
1. 任何 DROP/TRUNCATE/ALTER 必须写全 schema
   禁止：DROP TABLE papers
   必须：DROP TABLE scifact_eval.papers

2. 建库脚本启动时打印并校验：
   current_database()
   current_schema()
   目标 schema
   目标表是否存在

3. DDL 前必须 dry-run：
   只打印将执行的 SQL 与目标对象，不执行

4. 生产 DSN 上禁止运行建库脚本
   建库只允许独立数据库/独立角色

5. DROP 必须带显式 --allow-destructive
   没有该参数直接拒绝

6. 一次 DROP 只允许一张表
   禁止多表 CASCADE 列表

7. DDL 前自动 pg_dump 目标库
   pg_restore -l 验证通过才允许继续
```

### 6.2 代码层

```text
scripts/sql_guard.py
  - 扫描 DROP/TRUNCATE
  - 未带 schema 直接报错
  - 多表 DROP 报错
  - 目标库名白名单
```

CI：

```text
grep -R "DROP TABLE" scripts build_db
未限定 schema -> fail
```

### 6.3 权限层

```text
生产写入角色与建库角色分离
建库角色只能访问 build_* 数据库
生产 DSN 不进入建库脚本环境
```

### 6.4 评审层

PR 模板增加：

```text
[ ] 是否包含 DROP/TRUNCATE/ALTER
[ ] 是否 schema 限定
[ ] 是否在克隆库演练
[ ] 是否有备份与恢复验证
[ ] 是否影响 public
```

### 6.5 数据层

```text
建库前：pg_dump -Fc + restore -l
建库后：count 对账
切换前：只读 smoke + 回滚演练
```

## 7. 开发规范调整

### 7.1 禁止事项

```text
禁止在生产 DSN 上跑临时 DDL
禁止未限定 schema 的 DROP
禁止多表 CASCADE
禁止无备份的 schema 变更
禁止把评测库和主库放在同一 schema
```

### 7.2 必须事项

```text
建库使用独立数据库
DDL 走 migration 或受控脚本
变更前备份
变更后对账
失败可回滚
```

### 7.3 事故响应

```text
先停止写入/任务
再确认影响范围
再恢复
最后复盘
```

## 9. 结论

这不是“手滑”，是流程缺失：

```text
脚本可以无 schema 限定地 DROP
生产 DSN 可以被建库脚本直接使用
DDL 前没有备份和 dry-run
```

这三件事同时存在，事故是必然的。

我的责任：

```text
在生产环境执行了未限定的破坏性 DDL
```

修复顺序：

```text
1. 已修 SciFact DROP（schema 限定）
2. 加 sql_guard + CI
3. 建库脚本隔离 DSN
4. 备份/恢复门禁
5. PR 模板
```

在这之前，不再对生产执行任何 DDL。

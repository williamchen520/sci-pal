# 异步「下载 + 入库 + 向量化」设计

> 起因：2026-10-25 批量下载把 Flask 主线程卡死、进程被看门狗重启，SQLite 处在 delete journal 模式下留下半写状态；虽然备份救了回来，但暴露出「长耗时任务不能同步跑」。
> 目标：只提交不等待、状态可查、分批提交、失败只回滚当批、WAL 防损坏。

---

## 1. 能力与接口

| 入口 | 行为 |
|---|---|
| `POST /api/ingest` | body `{pmc_ids, batch_size?}`，**立即**返回 `{ok, task_id}`（202），后台线程执行 |
| `GET /api/ingest/<task_id>` | 返回任务行：`status / total / processed / imported / failed / current / error` |
| `POST /api/ingest/<task_id>/cancel` | 置取消标记，worker 在**批次之间**退出 |
| MCP `download_and_index(pmc_ids, batch_size=5)` | 转发 POST，返回 task_id |
| MCP `check_ingest_status(task_id)` | 转发 GET，供模型轮询 |

`status` 取值：`queued → running → completed | partial | failed | cancelled`。
`partial` 表示有批次成功也有失败，**成功的批次不会被回滚**。

---

## 2. 批处理与事务

```
for batch in chunks(pmc_ids, batch_size):
    download + parse   # 单篇失败只记入 failures，不中断批次
    with conn:         # BEGIN ... COMMIT：整批一个事务
        upsert papers + paragraphs
    embed(batch)       # 写 Chroma，失败只记录（索引可重建）
    update ingest_tasks (processed/imported/failed)
```

- **每 5 篇一次提交**，不会等 25/100 篇全跑完；
- 任何一批抛异常 → `conn.rollback()`，只丢这一批，前面的批次已提交；
- 任务行本身也随批次更新并提交，所以进程被杀后仍能看到「已完成到第几批」。

## 3. 防损坏

- `PRAGMA journal_mode=WAL` + `synchronous=NORMAL`（连接即设置，持久生效）；
- 每批一个短事务，避免长写锁；
- 取消只在批次边界生效，不会杀在事务中间。

## 4. 实测

| 用例 | 结果 |
|---|---|
| 提交 10 篇（batch=5） | 202 立即返回；`processed 10 / imported 9 / failed 1`（PMC13695442 下载失败），耗时约 12.5 min（首次，含模型加载） |
| 提交 25 篇（batch=5） | `processed 25 / imported 23 / failed 2`，耗时 **159 s**（进程已预热） |
| 批次推进 | 25 篇用例中 5→10→15→20→25 逐批上报，失败不阻塞后续批次 |
| 数据库 | `journal_mode=wal`；papers 2,086 → 2,110；paragraphs +2,292；vectors +2,292 |
| FTS | paragraphs_fts 触发器自动同步（+2,293）；papers_fts 无触发器，**需手动增量同步**（本次已补 24 行） |

失败样本：`PMC13695442`、`PMC13692791` 两次都报 `download failed`（NCBI 无 OA 全文或临时失败），属于单篇隔离，不影响其余 23 篇。

## 5. 已知限制

1. **papers_fts 没有触发器**：新论文只进 `papers` 表，标题检索会漏；要么加触发器，要么在批处理后补 `INSERT ... WHERE NOT IN`（本次手工补过）。
2. **取消粒度是批次**：单批内 5 篇不可中断（与 T-5 的「阶段内不可中断」同类）。
3. **无重试**：下载失败直接记 failures；后续可加指数退避重试。

### 5.1 已解决：ingest 交给常驻 worker

`POST /api/ingest` 现在默认只把 `ingest-<task_id>.job.json` 写进 `data/runs/_queue`，由常驻 worker 进程执行（`SCIPAL_INGEST_INLINE=1` 可退回进程内线程）。

实测（7 篇新 PMCID，batch=5）：

```
提交延迟      231 ms（Flask 只写一个 JSON 文件）
worker 执行   4 篇入库 / 3 篇下载失败（单篇隔离）
papers        +4
health 探测   median 38 ms，max 7.8 s（期间 worker 首次加载嵌入模型）
```

对比之前「在 Flask 内跑」：提交仍是毫秒级，但模型加载与 embedding 不再占用 API 进程的 GPU/解释器；health 的 7.8 s 毛刺来自 worker 冷启动，之后同一 worker 复用模型。

### 5.2 worker 常驻 + papers_fts 触发器

- `scripts/install_worker_autostart.ps1`：注册计划任务 `SciPalWorker`（登录后 30s 启动，`--log-file logs\worker.log`，无限时，异常重启 3 次）。移除：`Unregister-ScheduledTask -TaskName SciPalWorker`。
- 已实测：计划任务拉起 worker → 通过 API 提交 ingest → worker 消费队列 → `processed/*.result.json` 与日志均有记录。
- `build_db/build_fts.py` 现在同时重建 `papers_ai/ad/au` 触发器：入库/改名/删除论文时 `papers_fts` 自动同步，不再需要手工补行（存量已回填）。

## 7. 验收发现与修复（2026-10-26）

验收时 worker 里的 ingest 反复「挂住」：任务停在 running、无 batch 进度。栈采样定位到：

```
ingest.py:254  DELETE FROM paragraphs WHERE paper_id = ?
```

**根因不是 Chroma，也不是 GPU**：`paragraphs_ad` 触发器用 `WHERE para_id = ?` 删除 FTS5 行，而 `para_id` 是 `UNINDEXED` 列 → 每删一行扫 145k 行；重导入一篇有 100+ 段的论文就是上千万行扫描，表现为无限卡住。

修复：

1. 批次内先 `DROP TRIGGER paragraphs_ad`，用集合化 `DELETE FROM paragraphs_fts WHERE para_id IN (SELECT ...)` 删 FTS 行，批次结束再恢复触发器；
2. `INSERT OR REPLACE INTO papers` 默认不触发 DELETE 触发器，补显式 `DELETE FROM papers_fts WHERE paper_id = ?`，避免 papers_fts 重复累积（验收时清掉 10 行重复）；
3. 每批 embed 加 `batch_timeout`（默认 300s），超时标记失败而不是无限等待；
4. 单写者：worker 通过 `POST /api/embed` 让 Flask 代写 Chroma（`SCIPAL_INGEST_EMBED=local` 可退回本地）。

验收结果：同一批 2 篇（已存在的论文，触发 DELETE+重插）**9.8 秒完成**，`papers == papers_fts == 2114`。

### 7.1 教训

- 「挂住」先用栈采样定位，不要先猜 GPU/锁；
- FTS5 `UNINDEXED` 列上的 DELETE 是 O(n)，批量写必须按集合删；
- REPLACE 不触发 DELETE 触发器，这条容易漏。

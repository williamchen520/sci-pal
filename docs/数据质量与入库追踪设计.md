# 脏数据治理与入库追踪设计

> 日期：2026-11-07  
> 目标：10k/更大规模入库时，脏数据可拦截、可隔离、可追踪、可复现  
> 原则：不静默删除，不污染主库，不阻断整批

---

## 1. 目标

```text
入库前：去重、元数据校验、许可/来源校验
解析后：结构/文本/编码校验
入库后：引用完整性、embeddings、FTS 校验
全过程：批次、条目、原因、版本可追踪
```

非目标：

```text
不做人工全文审稿
不自动删除源文件
不用 LLM 做最终裁决
```

---

## 2. 脏数据分类

| 类别 | 例子 | 处理 |
|---|---|---|
| 重复 | PMCID/DOI/标题重复、近重复 | 拒绝/合并 |
| 元数据缺失 | 无标题、无年份、无 DOI | 隔离 |
| 元数据异常 | 年份越界、标题乱码 | 隔离 |
| 许可/来源 | 非 OA、来源不可信 | 拒绝 |
| 解析失败 | 空 XML、截断、0 段落 | 隔离 |
| 结构异常 | 无摘要、无章节、段落为 0 | 隔离/告警 |
| 文本异常 | 乱码、HTML、页眉页脚、参考文献混入 | 修复/隔离 |
| 重复文本 | 段落重复、模板 boilerplate | 修复/告警 |
| 非研究内容 | poster、erratum、广告 | 拒绝/隔离 |
| 引用完整性 | 段落无 paper、句子无段落 | 阻塞 |
| 向量异常 | 缺失、零向量、维度错误 | 阻塞/重跑 |
| 检索异常 | tsvector 空、FTS 索引缺失 | 告警 |

## 3. 模块边界

独立模块：

```text
services/ingest_quality/
  __init__.py
  models.py        IngestItem / Finding / Severity
  registry.py      rule registry
  rules/
    manifest.py    去重、元数据
    structure.py   段落/章节/摘要
    text.py        编码、乱码、boilerplate
    integrity.py   跨表引用
    vectors.py     embedding 完整性
  runner.py        run(stage, items) -> report
  store.py         PG 追踪表读写
```

不侵入：

```text
build_db/import_jats_pg.py
build_db/build_database_pg.py
build_db/build_embeddings_pg.py
```

只加钩子：

```text
pre_ingest
post_parse
post_store
```

## 4. 规则接口

```python
class Rule(Protocol):
    code: str
    stage: str          # pre_ingest | post_parse | post_store
    severity: str       # block | quarantine | warn | repair
    def check(self, item, conn) -> list[Finding]: ...
```

Finding：

```text
code
severity
message
field
evidence
auto_fixable
```

---

## 5. 处理策略

```text
block       阻止入库
quarantine  写入隔离区，人工复核
warn        入库但标记
repair      安全修复后入库
```

安全修复只允许：

```text
Unicode NFKC
空白压缩
DOI 小写/去前缀
HTML 标签剥离
标题规范化
```

不允许自动：

```text
改年份
补 DOI
删段落
合并作者
```

## 6. PG 追踪表

```sql
CREATE TABLE ingest_runs (
  run_id          text PRIMARY KEY,
  source          text NOT NULL,
  started_at      timestamptz NOT NULL DEFAULT now(),
  finished_at     timestamptz,
  status          text NOT NULL,
  stats           jsonb NOT NULL DEFAULT '{}'::jsonb
);

CREATE TABLE ingest_items (
  run_id          text NOT NULL REFERENCES ingest_runs(run_id),
  item_key        text NOT NULL,
  source_url      text,
  checksum        text,
  parser_version  text,
  status          text NOT NULL,
  reasons         jsonb NOT NULL DEFAULT '[]'::jsonb,
  created_at      timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (run_id, item_key)
);

CREATE TABLE ingest_findings (
  id              bigserial PRIMARY KEY,
  run_id          text NOT NULL,
  item_key        text NOT NULL,
  code            text NOT NULL,
  severity        text NOT NULL,
  detail          jsonb NOT NULL DEFAULT '{}'::jsonb,
  resolved_at     timestamptz,
  created_at      timestamptz NOT NULL DEFAULT now()
);
```

索引：

```sql
CREATE INDEX idx_ingest_items_status ON ingest_items(status);
CREATE INDEX idx_ingest_findings_code ON ingest_findings(code, severity);
```

## 8. 批次集成

```text
1. manifest 去重
2. pre_ingest 检查
3. 200 篇/批导入
4. 每批 post_parse 检查
5. 每批 post_store 检查
6. 写 run/item/finding
7. 批间暂停
```

阻断条件：

```text
block 比例 > 1%
quarantine 比例 > 10%
app/PG 延迟异常
```

否则继续下一批。

## 13. 客户端批量导入场景

这不是防程序员，是防客户端误操作。

核心原则：

```text
能读入的先入库
有问题的显式标记
只对无法使用/明确重复的拒绝
不静默丢弃
```

### 13.1 条目状态

```text
clean        正常
warning      可用，但有质量提示
needs_review 已入库，建议人工复核
duplicate    重复，不新建，关联已有 paper
rejected     无法解析/空内容，未入库
```

默认：

```text
clean / warning / needs_review 都入库
duplicate 不新建
rejected 才不入库
```

### 13.2 papers 标记

新增列：

```sql
ALTER TABLE papers ADD COLUMN quality_status text NOT NULL DEFAULT 'clean';
ALTER TABLE papers ADD COLUMN quality_flags jsonb NOT NULL DEFAULT '[]'::jsonb;
ALTER TABLE papers ADD COLUMN quality_checked_at timestamptz;
```

示例：

```json
{
  "quality_status": "warning",
  "quality_flags": [
    {"code": "DQ005", "message": "year missing"},
    {"code": "DQ107", "message": "duplicate paragraph ratio 0.18"}
  ]
}
```

### 13.3 客户端看到什么

批量导入返回：

```json
{
  "batch_id": "...",
  "total": 120,
  "clean": 102,
  "warning": 11,
  "needs_review": 5,
  "duplicate": 2,
  "rejected": 0,
  "items": [
    {"filename": "x.pdf", "paper_id": "...", "quality_status": "warning", "flags": ["DQ005"]}
  ]
}
```

论文详情页：

```text
质量标记 badge
可展开查看原因
可人工修正元数据
可标记“已复核”
```

### 13.4 不阻断整批

```text
单条失败不影响其他条目
批量任务继续
最终给汇总
```

只有整批级问题才停：

```text
存储不可写
数据库不可用
文件全部不可读
```

### 13.5 重复处理

```text
同一 PMCID/DOI/标题
-> 不新建 paper
-> 返回 duplicate + existing_paper_id
-> 客户端提示“已存在”
```

### 13.6 人工复核

```text
needs_review -> 用户确认 -> quality_status=reviewed
warning      -> 可保留
rejected     -> 可修复后重试
```

### 13.7 存量数据

```text
先 backfill 扫描
只标记，不删除
按 code 统计
逐步修复
```

### 13.8 管理接口

```text
POST /api/ingest/batches
GET  /api/ingest/batches/<batch_id>
GET  /api/papers/<paper_id>/quality
POST /api/papers/<paper_id>/quality/review
```

## 14. 两种运行模式

### 后端导入（strict）

```text
先清洗
再校验
不合格就修复/拒绝
失败写日志并重试
```

不做：

```text
批次报告
逐条 finding
客户端 badge
人工复核队列
```

后端目标是：

```text
干净入库
可重跑
```

### 客户端导入（advisory）

```text
逐条检查
逐条标记
批次汇总
可复核
可修正
```

才需要：

```text
ingest_runs
ingest_items
ingest_findings
quality_status
quality_flags
```

### 共用

```text
规则定义
文本清洗函数
去重函数
```

不共用：

```text
编排
存储
UI
```

## 15. 后端 10k 的做法

```text
manifest 去重
-> 预检
-> 解析
-> 清洗
-> 200 篇/批入库
-> 失败重试
```

只保留运行日志，不建完整追踪表。

## 16. 客户端批量导入的做法

```text
上传
-> batch_id
-> 逐条检查
-> 能入的入
-> 标记 warning/needs_review
-> duplicate 关联已有
-> rejected 单独报告
-> 用户复核
```

这才需要完整追踪。

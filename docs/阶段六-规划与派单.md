## 0. 为什么是这三件事

阶段五把「通路」修好了，剩下的是**能力缺口**。按「用户能感知到什么」排序，而不是按代码美观度：

| 阶段 | 内容 | 用户能感知的变化 | 依赖 |
|---|---|---|---|
| **6-A** | 任务持久化（review 任务从内存 dict 迁到 SQLite `tasks` 表） | 重启 Flask 后，之前拿到的 `task_id` **不再 404**；综述/大纲/问答/多跳的结果能跨重启查到 | 无 |
| **6-B** | 论文入库链路挂 MCP（列本地 PDF + 解析） | 模型可以自己看「有哪些 PDF 没入库」并触发解析，不必回 Web UI 点 | 依赖 6-A（解析要异步，异步要用持久任务存储） |
| **6-C** | `scipal-guard` 独立 server（领域词表校验） | 结论能按领域词表核一遍，不只靠 LLM 自证 | **待定**：词表数据源需要用户决策 |

**顺序不能换**：6-B 的异步解析要用任务存储，先做 6-B 等于把异步写两遍（先用内存版、再迁库）。

## 2. 阶段六-B：论文入库链路（**代码已交付；验收「条件通过」—— 阻塞项见下**）

> 🔴 **验收结论（2026-10-25）**：代码按工单全部达标（快路径 / 串行化 / 对账 / 校验 / 27 断言全过），
> 但**「未解析文件 → 解析 → 入库」主链路仍然不通**：`research.db` 里三个遗留触发器
> `paragraphs_ai/ad/au` 引用 `section_level1/2/3`，而 `paragraphs_fts` 实际列是 `section_l1/section_l2`
> → 任何 `paragraphs` 插入都会报 `table paragraphs_fts has no column named section_level1`。
> 该缺陷**是既有的**（未改动的同步路由 `/api/papers/parse` 同样 500、同一句错误）。
> 修复工单：**`docs/工单-6B阻塞-段落FTS触发器修复.md`**。
> D-2 修好并按该工单第三节 9 项复验后，本节状态才可改为「通过」。
> 验收细节见 `docs/工作日志/2026-10.md`（2026-10-25 条目）。

工单：`docs/工单-阶段六B-论文入库接入.md`

> 解析耗时已实测（2026-10-25 13:15，临时副本、未写库）：6.3 MB → **23.9 s**、3.1 MB → **11.7 s**，
> 约 **3.8 s/MB** → 16 MB 以上必然顶穿 MCP 的 60 s，异步不是可选而是必须。

已核过的事实（2026-10-25）：

| 项 | 实测 |
|---|---|
| `POST /api/papers/parse` | **收 JSON body 的 `filename`**（`api_server.py:1655`），不是 multipart —— 已做路径穿越校验，MCP **可以直接传文件名** |
| 同步还是异步 | **同步**：docling 解析 + 写库，一次调用内完成（**6-B 未改动它，保留作对照基线**） |
| 耗时 | 约 **3.8 s/MB**（6.3 MB → 23.9 s）→ >16 MB 顶穿 60 s，故必须异步 |
| `GET /api/papers/local` | 扫描 documents 目录，返回 `{filename, parsed, paper_id, title, …}`，可直接做只读工具 |
| `/api/papers/import` | 真 multipart，**这个才传不了文件流** → 维持不做 |

**落地形态**：**只读工具** `list_local_papers`（返回裁剪为 6 个精简字段 + `limit` 上限 + 「已截断」标注）
+ **异步解析** `parse_paper`（新端点 `POST /api/papers/parse_async`，立即返 `task_id`，用
`review_task_status` 轮询，复用 6-A 的持久化存储），工具加到 `scipal-search`（**8 → 10**，第 3 次破例）。

**6-B 附带改动**：`REVIEW_TASK_TYPES` 改名 `PERSISTED_TASK_TYPES` 并加入 `parse_paper`
（`services/review/task_manager.py` 与 `api_server.py` **两处必须完全一致**）；启动对账范围随白名单走，
`download_online` **永远不进白名单**（它由 `services/search/online_downloader.py` 自行管理）。

**实测结论**：校验早于返回 `task_id`（空/穿越/不存在 → 同步 400/400/404）；已解析文件走
`already_parsed` 快路径 0.135 s；`_parse_lock` 串行化生效（第二个任务 progress 显示「排队中」）；
docling 模型常驻，任务结束后 RSS 不回落（1123.6 → 2385.7 MB）；对账只收 `parse_paper` 的僵尸
`running`，`download_online` 不受影响。

> ⚠️ 一个修正：`docs/DSH插件化-路线图.md` §2.4 原写「`/api/papers/parse` … `/api/papers/import` 是 multipart，
> MCP 传不了文件流」，把两件事混了 —— **multipart 的是 `import`，`parse` 只要文件名**。
> 已在本次一并改正。

## 4. 派单纪律（沿用阶段五的教训）

1. **一次只派一个阶段**，验收通过才派下一个；工单里写明「本工单现在就执行，不是下一轮」。
2. 每个工单的「零、背景事实」都现查核实、带行号，CodeBuddy **直接采信不重复查仓库**。
3. 验收一律**自跑**：重启、kill、并发实测，不看交付报告自述；
   尤其「改完没提交」「计数口径错」「文档重写把更正写回去」这三类它反复犯的错。
4. 业务代码改动必须**逐条列出**改了什么、没改什么，写进验收报告。

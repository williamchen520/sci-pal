### 根因（已定位到行，写进工单文末）

`launch_guard()` 接管分支（`scripts/sciPal_watchdog.py:643-664`）：

```python
log(f"发现过期拉起守卫（{holder or '内容不可读'}），接管")
try:
    LAUNCH_GUARD_FILE.unlink()     # 盲删：删的是「磁盘上现在那个」，不是「你判定为 stale 的那个」
except Exception:
    pass
if not _create_guard_exclusive():  # 文件已被自己删掉 → O_EXCL 必然成功
```

- 两个进程读到同一份 stale → 都判「该接管」→ P1 删+建成功 → **P2 把 P1 刚建的文件删掉**，再建也成功 → 双开。
- **窗口被放大到约 1 s**：判定与动手之间要调 `launch_guard_holder_alive()` → `process_start_time()`
  （WMI/CIM，单次 0.5~1 s），所以「同时起」时基本必现。
- 修法（工单 T4-1'）：优先改成 **`msvcrt.locking` 操作系统级文件锁**（进程死即自动释放，stale 概念消失，
  不依赖 pid/创建时间）；若坚持 pid 文件，接管必须用 `os.rename` 抢占、**严禁盲删**。

## 八、残留（P3，不阻塞，建议下次顺手改）

`launch_guard()` 的 `finally` 是「UNLCK → close → `unlink()`」。**close 与 unlink 之间锁已经放开**：

```
W1: unlock + close            → 锁空出
W2: 抢到锁 → same_file 校验通过（文件还在）
W1: unlink()                  → 路径消失（W2 锁的是旧 inode）
W3: O_CREAT 造新 inode → 抢锁成功 → 也通过 same_file
→ W2、W3 同时进入 launch
```

需要**三个** contender 且 W2 恰好落在 close→unlink 的那几微秒里，实际极难触发（两个 contender 时不存在 W3）。
但它与首版是同一类错误（**在放开互斥之后动文件**），代价却是为了满足我给的 A5「不留残留」这条纯外观要求。

**建议**：不再 `unlink()` —— 守卫文件留着（513 B，内容不参与判定，完全无害），
A5 判据改为「**文件可残留，但不得被持有**」。这样这条路彻底没有窗口，`--status` 也能看到上次是谁、
更容易排查。**别为了「干净」引入竞态。**

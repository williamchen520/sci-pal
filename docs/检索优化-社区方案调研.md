# 检索优化：社区与论文方案调研

> Date: 2026-11-01  
> Scope: sentence FTS 延迟、两阶段召回、生产级检索后端。  
> Constraint: 当前数据规模约 65 万句子、3,300 论文，单机 PostgreSQL 16。

## 1. 结论先行

```text
当前不需要马上上 Elasticsearch/Milvus。
先把“数据库只做召回、Python 做精排”做对。
首选 ParadeDB pg_search（BM25）或现有 HybridSearch；
如果扩展不可用，再用 Elasticsearch/OpenSearch。
```

## 2. 社区方案

### 2.1 ParadeDB `pg_search`

- PostgreSQL 扩展，在 PG 内提供 BM25 风格检索与 top-k。
- 适合当前“PG 已有数据 + 不想引入第二套系统”的阶段。
- 需要安装扩展；当前 PG 只装了 `pg_trgm`，没有 `pg_search`。

参考：

- [ParadeDB repository](https://github.com/Blazearth/paradedb)
- [pg_search README (PGXN)](https://api.pgxn.org/src/pg_search/pg_search-0.15.19/pg_search/README.md)
- [ParadeDB top-k benchmark](https://github.com/paradedb/paradedb/blob/6e3efd5ad21750cf6857d7019ecbdf70c6cadda0/benchmarks/datasets/stackoverflow/queries/join_top_k_score_desc_low_selectivity/README.md)

### 2.2 PostgreSQL 原生 `ts_rank`

PostgreSQL 的 `ts_rank` 不是 BM25；它需要先取出匹配行，再排序。

- EXPLAIN 已确认走 `Bitmap Index Scan`，不是 Seq Scan。
- 成本在 bitmap heap scan + sort，而不是索引缺失。

参考：

- [PostgreSQL ts_rank slow thread](https://postgrespro.com/list/thread-id/1514792)
- [Two GIN applications](http://www.sai.msu.su/~megera/postgres/talks/Next%20generation%20of%20GIN.pdf)

### 2.3 Vespa multi-phase ranking

Vespa 的工业级做法就是：

```text
cheap first-phase retrieval
→ top-k
→ expensive second-phase ranking
```

这与我们的“GIN 粗排 + Cross-Encoder 精排”一致。

- [Vespa multi-phase ranking](https://vespa.ai/ai-search-platform/architecture/multiphase-ranking/)
- [Vespa cross-encoder reranking blog](https://blog.vespa.ai/improving-llm-context-ranking-with-cross-encoders/)

### 2.4 Elasticsearch / OpenSearch

成熟方案：

```text
BM25 top-k
→ cross-encoder / rerank
```

代价是第二套系统、同步链路和运维。当前数据规模还不值得。

参考：

- [Meilisearch comparison](https://www.meilisearch.com/docs/resources/comparisons/alternatives)

### 2.5 Meilisearch / Typesense

优点：部署简单、搜索快。  
缺点：科学文献需要的 BM25 可调性、复杂过滤、排序解释不如 ES/Vespa。

适合“轻量产品搜索”，不适合当前 claim/evidence 的复杂检索。

## 3. 论文与竞赛方案

### 3.1 ClimateCheck 2025 winning system

- BM25 多路召回
- BGE-Reranker ensemble
- LLM analysis

这正是两阶段检索，不是单靠数据库 rank。

- [Winning ClimateCheck](https://aclanthology.org/2025.sdp-1.25.pdf)

### 3.2 Lit3R

面向科学文献的 Retrieve–Relate–Read 流程，同样强调先检索、再关系/阅读，而不是把全部排序压给一个 FTS 查询。

- [Lit3R](https://browse-export.arxiv.org/pdf/2609.16912)

### 3.3 PaperQA2

科学问答系统，采用文献检索 + 上下文重排 + 证据生成的分层路线。

- [PaperQA2 docs](https://docs.edisonscientific.com/paperqa/readme.md)

## 4. 直接用于 SciPal 的方案排序

### 方案 A：现有 `HybridSearch`（推荐先复用）

项目已经有：

```text
SQLite FTS5 BM25
+ Chroma 向量
+ RRF
+ Cross-Encoder
```

这已经是社区标准的两阶段/混合检索。  
不应该在 v2 上重新造一个更弱的 sentence ranker。

建议：

```text
用现有 HybridSearch 做候选召回
→ 再用 BGE reranker
→ 保留 sentence FTS 只做溯源
```

### 方案 B：ParadeDB `pg_search`

如果要在 PG 内解决 `ts_rank`：

```text
安装 pg_search
→ BM25 top-k
→ Cross-Encoder
```

优点是保留 PG 数据模型，不需要 ES。

风险：

```text
扩展安装/版本兼容
生产容器需要重建
```

### 方案 C：Elasticsearch/OpenSearch

数据量到千万/上亿，或需要复杂文本分析、聚合、同义词、多语言时再上。

### 方案 D：Vespa

如果要做“多阶段 rank + 大规模在线”，Vespa 是最贴近的架构；运维复杂度高。

## 5. 不建议现在做

```text
分区表：65 万句子还不需要
Milvus：纯向量，不解决 BM25 召回
读写分离：当前不是高并发生产
Kafka：当前请求量不需要
GPU：先解决候选生成，再谈精排吞吐
```

## 6. 下一步建议

```text
1. 不继续调 ts_rank 参数
2. 用现有 HybridSearch 在 20 query 上做基线
3. 对比：HybridSearch vs paragraph_fts vs rank_cd+rerank
4. 若 HybridSearch 胜出，生产直接用现有检索
5. 若仍不够，再评估 pg_search 或 ES
```

T-2 把 `_parse_lock` 下沉成「唯一一把锁」，前提是**一个进程**。验收时发现看门狗能堆出

## T4-1（P1）看门狗拉起必须互斥：任何路径都不许堆出第二个实例

### 现状（已定位到行）

| 位置 | 行为 | 问题 |
|---|---|---|
| `run_daemon()` `:614-617` | `acquire_lock()` 失败即 `return` | 有互斥，但只在 daemon 之间 |
| `run_daemon()` `:648-651` | `port_listening()` → 本轮不拉起 | 只挡「已有人在监听」，挡不住「两个 run 同时冷启动」 |
| **`run_once()` `:591-609`** | **不看锁、不看端口**，`probe()` 失败就 `launch()` | **堆实例的直接原因** |

日志证据（`logs/sciPal_watchdog.log`）：

```
14:57:28 已拉起 api_server.py（pid=8384）/ 同一秒 已拉起（pid=19968）
15:07:15 已拉起 api_server.py（pid=2300）
15:07:17 已拉起 api_server.py（pid=27880）   ← 2s 后又拉一个，最终 2 个都在 LISTENING
```

`F-1 wait_until_ready()` 只保证**单个 run 内部**不重复拉，管不了 run 之间。
Windows 的 `SO_REUSEADDR` 允许重复 bind，所以两个实例**都能 bind 成功、都判「已就绪」**。

### 要做的

1. 新增**拉起互斥守卫**（与 daemon 的持久锁分开，别混用）：
   - 文件：`logs/sciPal_launch.guard`，内容 `{"pid": <pid>, "start": <进程创建时间戳>, "at": <iso>}`。
   - 获取用 `O_CREAT|O_EXCL`（原子）；获取失败时读文件判 `pid_alive` + 创建时间是否匹配，
     **不匹配视为 stale 直接接管**（防强杀留下的尸检文件把看门狗永久锁死）。
   - 用 `contextmanager` 包住 `launch() + wait_until_ready()` 这一段，`finally` 里删除。
2. `run_daemon()`：`launch() + wait_until_ready()` 整段包进守卫；守卫被占 → 打日志、本轮跳过（进冷却）。
3. `run_once()`：
   - **先判 daemon 锁**：`read_lock()` 里 holder 存活 → 打「已有看门狗在运行（PID x），`--once` 不重复拉起」，
     `probe()` 成功则 `exit 0`，失败也**不许 launch**（那是 daemon 的职责），`exit 1`。
   - 再判 `port_listening()` → 打「端口已被占用，可能在冷启动」→ `exit 0`。
   - 两道都过 → 进拉起守卫 → `launch()` → `wait_until_ready()`。
4. `--status` 增加两行：`launch guard`（内容/PID/是否 stale）、`instance count`（监听 PID 列表与个数）。

### 验收（不许用 health 200 判单实例，必须数监听 PID）

| # | 场景 | 断言 |
|---|---|---|
| A1 | 先 kill 所有 `api_server.py`，**同一秒并发跑两次 `--once`** | 60 s 内每 2 s 采样 `Get-NetTCPConnection -LocalPort 5000`，**监听 PID 个数最大值 == 1**；日志恰好 **1 条**「已拉起」，另一条是「守卫被占」 |
| A2 | daemon 存活时跑 `--once` | `api_server.py` 进程数**不变**；日志有不重复拉起的说明；**`exit 0`**（判定口径统一：`--once` 只要有「不 launch」的正当理由就 `exit 0`，只有「尝试拉起但未在超时内就绪」才 `exit 1`） |
| A3 | 无 daemon、无监听时跑 `--once` | 能拉起、等到就绪（打印实际耗时）、**单实例** |
| A4 | `taskkill /F` 强杀持有守卫的进程 → 再跑 `--once` | 能接管 stale 守卫并拉起（**不被死文件卡住**） |
| A5 | 正常退出后 | `logs/sciPal_launch.guard` **不存在** |
| A6 | `--status` | 有 `launch guard` 与 `instance count` 两行，`instance count` 与 `netstat` 一致 |

> A1 的关键：**两次 `--once` 要真并发**（`Start-Job` 或 Python `subprocess.Popen` 同秒起），
> 串行跑两次必然只有一次会 launch，测不出问题。

## T4-2（P2）「排队中」进度立刻被覆盖 → 排队不可观测

### 现状

`api_server.py` `run_task()`（`:1925-1935` 附近）：

```python
if _parse_lock.acquire(blocking=False):
    _parse_lock.release()
else:
    task_manager.update_progress(task_id, "排队中（前面还有解析任务）")

if task_manager.is_cancelled(task_id):
    ...
task_manager.update_progress(task_id, "解析中（docling）…")   # ← 无条件覆盖，中间无阻塞
result = _parse_and_store(pdf_path, filename, before_store=_before_store)   # ← 阻塞在这里
```

后果：被锁挡住的第二个任务**全程显示「解析中（docling）…」**。
实测（3.60 MB 探针，A 先起、B 晚 0.4 s 起，B 实际排队 40 s）：B 提交后 1.8 s 采样即
`progress='解析中（docling）…'`，全程 21 次采样**零次**出现「排队」。

### 要做的

1. `_parse_and_store(pdf_path, filename, before_store=None, on_acquired=None)`：
   在 `with _parse_lock:` 之内的**第一行**调用 `on_acquired`（早于 `ParserOrchestrator()` 构造）。
   docstring 写清调用时机（已拿锁、未解析）与异常传播规则（回调抛异常即放弃本次解析，锁自动释放）。
2. 异步路由：删掉 `update_progress("解析中（docling）…")` 那一行，改为
   `on_acquired=lambda: task_manager.update_progress(task_id, "解析中（docling）…")`。
   **「排队中」那行保留**（试抢失败才写）。
3. 同步路由：不传 `on_acquired`（它没有 task 可更新），行为不变。

### 验收

| # | 场景 | 断言 |
|---|---|---|
| B1 | **单实例**下两个未解析文件：A 先提交，0.4 s 后 B 提交 | B 的 `progress` 在排队期间连续 **≥3 次**（间隔 3 s）读到 **「排队中（前面还有解析任务）」** |
| B2 | 同上 | B 进入解析后 `progress` 变为「解析中（docling）…」**且只变一次** |
| B3 | 取消 B（还在排队时） | B 终态 `cancelled`、`papers` 无 B 行（排队期间取消不许漏进写库） |
| B4 | 单任务正常路径 | `progress` 依次是「解析中（docling）…」→「写入数据库…」，**不出现「排队中」** |
| B5 | 回归 | `selftest` 27/27、`precheck` 0、`papers` 565 / `paragraphs` 52629 / `paragraphs_fts` 50950 回基线、探针 PDF 全删 |

## 0. 一句话结论

**不是"CPU 不够"，也不是"内存不够"，是"所有重活挤在一个 Python 进程里"** ——
24 核只用到 1.4 核，41 GB 内存空着，可 `/api/health` 仍然能被阻塞到 **102 秒**；
被取消的任务在取消后 **又跑了 7.7 分钟**；
而且今晚第一次抓到 **进程在重活期间直接消失（无 Traceback）**，看门狗 1 秒后才拉起新实例。

## 3. 证据 B：轻请求被拖到分钟级，而 CPU 只用了 1.4 核

### B-1 三并发 `generate_review`（fresh 实例，pid 4232，150 s 采样）

| 指标 | 实测 |
|---|---|
| 空闲基线 health | med **10 ms** / max 30 ms（112 线程，RSS 1.1 GB） |
| 三次提交延迟 | **0.13 s / 0.16 s / 0.12 s**（提交本身没问题） |
| 有载 health | n=49，min 0.01 s，med 0.05 s，p95 1.66 s，**max 102.76 s** |
| 有载 task-poll | med 0.05 s，p95 0.52 s，**max 48.27 s** |
| 线程数 | 112 → 141 → **166**（3 个任务涨了 54 条） |
| CPU | 采样窗 245 s 累计 343 s → 平均 **140%**（= 1.4 核 / 24 核） |

### B-2 单并发 `generate_review`（pid 23620，120 s 采样）

| 指标 | 实测 |
|---|---|
| 提交 | 0.18 s |
| health | med 0.04 s，p95 0.31 s，**max 102.58 s** |
| CPU | 154 s / 156 s → **99%**（= 1 核） |

⚠️ 该轮采样窗口内发生了一次**进程重启**（见证据 D），因此"单并发 max 102.58 s"这个数**打折**：
其中至少一次长等待与重启重叠。但"**一个**重活也能把轻请求拖到几十秒"这一点与 B-1 一致。

**判定**：CPU 只占 1.4 核、内存空 41 GB，说明瓶颈**不在算力**，而在
①Python 单进程的 GIL/线程调度；②进程在重活期间被重启（见 D）。

## 4. 证据 C：取消只改数据库状态，工作线程照样跑完

| 观测 | 数据 |
|---|---|
| 取消时刻 | `1837d3b2` 于 **21:38:06** 取消（`cancelled`，progress 停在「检索文献...」） |
| 之后进程状态 | 一直被强杀于 **21:45:50**，期间该线程**持续工作 7 分 44 秒** |
| CPU 侧证 | EXP-5 中取消发生在 t=11.6 s，到采样结束（245 s）该实例**又烧了 282 s CPU** |
| 终态 | `1837d3b2 cancelled`；另两个 `40cf9a8f` / `f666e514` 被杀时已推进到「撰写正文...」 |

也就是说：**UI 上点了取消、库里显示 cancelled，机器却还在为它干活**（包括后续 LLM 撰写、写库前的检查点），
既浪费 CPU/RAM，也让并发的其他任务更慢。这与 C-2 已写明的「阶段级取消」一致，但**阶段粒度太粗**：
`检索文献 → 证据抽取 → 大纲 → 撰写 → 校验` 五段里，只有边界检查，段内是原子的。

## 5. 证据 D（P0，新发现）：进程在重活期间静默消失

时间线（`logs/sciPal_watchdog.log` + `logs/sciPal_api.log`）：

```
21:48:58  看门狗拉起 api_server（pid=26576 → 实际解释器 23620）
21:49:03  报告"服务已就绪（等待 3.1s）"
21:49:37  服务不通（health 探测失败，listening pids=[23620]）← 端口在监听但探针不通
21:49:37 ~ 21:51:27  每 14s 一次"端口已在监听但探针未通过，本轮不拉起"（共 8 次）
21:51:41  出现两个监听 PID：[23620, 26288]     ← 双监听！
21:51:51  服务已恢复
...
21:56:16  提交 1 个 generate_review（EXP-8）
21:56:41  最后一条 health 200
21:56:50  服务不通（listening pids=[]）        ← 进程直接没了
21:56:51  看门狗拉起新实例 pid=16388
```

关键事实：
1. **无任何 Traceback**（近 300 行日志 `Traceback|MemoryError|Fatal` 计数为 0），
   Python 层没有抛错 → 属于原生层崩溃或被外部终止。
2. 死前进程只剩 **2 条线程**（`MainThread` idle + `tqdm_monitor`），其余线程全部消失
   （py-spy dump t=24.9 s 的快照）→ 那是**关停态**，不是正常服务态。
3. 21:49–21:51 那一段同样异常：**端口在监听、进程在、探针不通、持续约 2 分钟**，
   并且出现了**两个 PID 同时 LISTENING**（T-4 的守卫本应拦住重复拉起，这条要单独复核）。
4. 这两次异常都发生在**有重活的窗口**里。

**未定位**：可能是原生崩溃（torch/chromadb 的 C 层），也可能是外部（安全软件/宿主）终止，
也可能与我在 t=0–25 s 连续 `py-spy dump`（每次 0.3–5.7 s，Windows 上是调试器方式附加）有关。
**必须先取证再改代码** —— 否则任何并发改造都建立在"进程会莫名其妙消失"的流沙上。

## 8. 机制判定（排除了什么）

| 假设 | 判定 | 依据 |
|---|---|---|
| CPU 不够 | ❌ 排除 | 24 核，重活期间只用 1.4 核 |
| 内存不够 / 分页 | ❌ 排除 | 可用 41.3 GB，`PagesPerSec=0` |
| SQLite 写锁等待 | ❌ 排除 | `_connect(timeout=5)`，锁冲突会 5 s 抛 `database is locked`，不会等 100 s |
| 磁盘 I/O 慢 | ❌ 排除 | 模型权重加载本身只要 2–14 s，大头是 import/初始化 |
| GBK/编码、代理 | ❌ 排除 | 全部 `--noproxy`、`PYTHONUTF8=1` |
| **单进程 GIL + 长阻塞调用** | ✅ 主因（待 py-spy 定点） | CPU 1.4 核却 102 s 无法响应轻请求；`py-spy dump` 多次显示主线程 idle 在 `select()`，说明不是 accept 阻塞，而是**其他线程占着解释器/长 C 调用** |
| **进程被重启/消失** | ✅ 并存（P0） | 21:49–21:51 与 21:56:50 两次，均无 Traceback |
| 取消不停线程 | ✅ 确认 | 取消后仍干 7.7 分钟 / 282 s CPU |

## 9. 修复方向（三条，代价与收益都是量化的）

| 方案 | 做法 | 收益 | 代价 | 判断 |
|---|---|---|---|---|
| **A. 重活出进程**（推荐终点） | API 进程只做轻活（health / 提交 / 轮询 / 列表）；重活交给常驻 worker 进程（或进程池），状态继续走 SQLite `tasks` 表（C-2/6-A 已经铺好） | 轻请求彻底摆脱 GIL；重启 API 不再中断任务；崩溃隔离 | 架构改动大；worker 也要各自预加载模型（+1.1 GB/进程） | **阶段七的正解**，不适合今晚硬上 |
| **B. 进程内降低并发 + 切碎长调用** | 重活全局串行（`HEAVY_MAX_CONCURRENT=1`）+ 在长循环里插让步点 + 取消可以真正中断 | 改动小、可今晚做 | 只是缓解：单活也能造成 100 s 停顿（B-2），治不了根 | 作为过渡可以，但**不能当成"已修复"** |
| **C. 多进程 WSGI（waitress/gunicorn workers）** | 起 2–3 个进程，各自预加载模型 | 轻请求有独立进程兜底，改动中等 | 内存 ×N（1.1 GB/进程起）；`_parse_lock` 等**进程内锁全部失效**，需改成 DB/文件锁 | 折中方案，需先解决锁语义 |

**方向建议**：先做 P0 取证（A 的可行性取决于崩溃原因），再做 C 或 A；B 只作为"今晚可交付的止血"。

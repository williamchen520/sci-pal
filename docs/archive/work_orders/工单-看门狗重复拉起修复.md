## 一、故障现象（实测，2026-10-25 07:2x–07:4x）

```text
netstat -ano | grep ":5000.*LISTENING"
→ 同一时刻 3 个（最多时 8 个）python.exe 同时 LISTENING 在 0.0.0.0:5000
```

进程启动时间分布在 05:20:22 → 05:28:48，大约 **每 60~70 秒新增一对**（venv 启动器 + 系统 python worker）。

后果：

1. **每个实例都加载一套模型**：实测单个 Flask 常驻 1.4~2.9 GB，8 个实例会把内存吃穿。
2. **请求落到哪个实例不确定**：Windows 的 `SO_REUSEADDR` 允许重复绑定，所以没有 `Address already in use`
   把问题暴露出来 —— 是**静默**的。测试结果、轮询结果都可能来自不同实例（不同代码版本、不同任务内存）。
3. 任务状态（review `task_manager` 是**进程内内存 dict**）在不同实例间**不共享**，
   拿到 task_id 后轮询可能落到另一个实例 → 直接 404。

## 二、根因（已定位到行，不要重新排查）

`scripts/sciPal_watchdog.py`：

| 常量 / 位置 | 值 |
|---|---|
| `POLL_INTERVAL` | 10 s（`:58`） |
| `LAUNCH_COOLDOWN` | **60 s**（`:59`，注释写「> 冷启动 30–45s」） |
| `STARTUP_WAIT_TIMEOUT` | 180 s（`:60`，**只有 `--once` 模式用**） |
| `run_daemon()` | `:352` —— `launch()` 成功就 `last_launch = time.time()`，然后直接 `time.sleep(POLL_INTERVAL)`，**不等待服务真的就绪** |

**冷启动实测 ≈ 76 s**（2026-10-25 07:34 / 07:39 两次测量：从 kill 到 `/api/health` 变 200）。

→ **冷却期 60 s < 冷启动 76 s**：冷却一过，探针仍失败（服务还在加载模型），
守护进程就再拉一个；新旧两个实例因为 `SO_REUSEADDR` **都能绑定成功**，
于是每轮多一个，滚雪球。

三个因素叠加，缺一不可：

1. 冷却期短于真实冷启动（60 < 76）
2. daemon 拉起后**不等就绪**（`--once` 会等到 180 s，daemon 不会）
3. Windows `SO_REUSEADDR` 允许多实例绑同一端口 → 静默失败，没有报错兜底

## 三、修复要求

### F-1（必须）拉起后等到就绪，或把冷却期拉到冷启动之上

**推荐做法**（与 `--once` 对齐）：`launch()` 成功之后，在 `run_daemon()` 里循环探测
`probe()`，直到成功或超过 `STARTUP_WAIT_TIMEOUT(180s)`，再进入下一轮 sleep。
这样 `last_launch` 只在**真正就绪后**才计，天然杜绝重复拉起。

退而求其次：`LAUNCH_COOLDOWN` 改 ≥ 180 s。**但不推荐** —— 硬编码时长会随模型/硬件漂移。

### F-2（必须）拉起前先确认端口上没有别的实例

`launch()` 之前先做一次二次确认：若 `probe()` 已经成功，直接跳过本轮（现在就是这样，
但堆叠发生时探针是失败的，所以还需要 F-3）。

### F-3（强烈建议）启动前检测「已有实例在监听」

用标准库判断 5000 端口是否已被占用（例如尝试 `socket.connect_ex(("127.0.0.1", 5000))`，
或复用 `pid_alive()` 检查上次拉起的 pid 是否还活着）。
**若已有进程在监听但探针失败**，说明它还在冷启动/僵死 —— 此时**不要**再拉一个新的，
应记录日志并等待（让 F-1 的等待逻辑自然覆盖）。

### F-4（可选，但很有用）暴露一个自检开关

加 `python scripts/sciPal_watchdog.py --status`：打印当前锁内容、监听 5000 的进程数、
探针结果。方便以后一眼判断有没有堆积，不用再 `netstat`。

1
新论文接入 — 去重检查 + 版本检查 + 分配ID
已实现
📥 输入
新论文 PDF / XML / JSON（来自 PubMed / PMC / OpenAlex / 手动导入）
→
📤 输出
paper_record（含 paper_id + version + source + last_updated）
  • 去重检查：按 DOI / PMID / PMCID / arXiv ID 检查是否已存在。三级去重（PMCID→PMID→DOI），已存在则跳过或更新版本
  • 版本检查：如果已有旧版本，记录旧版本ID，标记为 superseded_by 新版本
  • 分配ID：paper_id = "paper_" + 唯一标识（如 PMC13607564_531e0063），version = 1（新版本）或递增
  • 元数据记录：source（来源）、download_time（下载时间）、last_updated（最后更新时间戳）
三级去重 (PMCID/PMID/DOI) 版本号递增 last_updated 时间戳

结构解析 — paper → section → paragraph → sentence
已实现
📥 输入
paper_record（PDF/XML 文件路径）
→
📤 输出
sentence_records[]（每个含 sentence_id + text + section_l1/l2 + paragraph_id + embedding）
  • XML解析（主力）：import_xml_v2.py 解析 JATS XML，提取 paper/section/paragraph/sentence 层级结构
  • PDF解析（备选）：6大解析引擎（Docling主力 + GROBID增强 + MinerU备选 + pdfplumber表格 + Journal Optimizer）
  • 句子切分：按句号/问号/感叹号切分句子，每个句子生成唯一 sentence_id = paper_id + "_para" + paragraph_index + "_sent" + sentence_index
  • 章节归属：每个句子记录 section_l1（一级章节）和 section_l2（二级章节），用于后续按章节检索
  • 句子级Embedding：用 bge-base-en-v1.5 生成768维向量，批量编码 batch_size=256
JATS XML 解析 6大PDF解析引擎 句子级切分 bge-base 768维 Embedding
import_xml_v2.py build_db/parsers/ (6个解析器) build_db/build_sentences.py

句子级近邻检索 — 每个新句子找 top-k 相似旧句子
已实现（复用检索层）
📥 输入
sentence_records[]（新句子 + embedding）
→
📤 输出
candidate_pairs[]（新句子 → [(旧句子, 相似度, 匹配方式), ...]）
  • 向量检索：每个新句子的 embedding → ChromaDB 检索 top-k（k=10）相似旧句子，余弦相似度
  • BM25全文检索：同时用 FTS5 做关键词匹配，补充向量检索遗漏的精确匹配
  • 实体匹配：scispacy NER 提取新句子中的基因/蛋白/疾病实体，在已有句子中做实体匹配
  • 结果融合：RRF（Reciprocal Rank Fusion, k=60）融合三路召回结果
  • 过滤自身：排除同 paper_id 的句子（不跟自己比），排除 sentence_id 完全相同的
ChromaDB 向量检索 (top-k=10) FTS5 BM25 全文检索 scispacy NER 实体匹配 RRF 融合 (k=60)
services/search/hybrid_search.py services/search/query_router.py services/search/unified_retriever.py

4
句子关系判定 — 重复/补充/支持/反驳/更新
待实现（核心难点）
📥 输入
candidate_pairs[]（新句子 + 相似旧句子列表）
→
📤 输出
sentence_relations[]（新句子 → [(旧句子, 关系类型, 置信度), ...]）
关系类型 判定方式 处理动作
🔴 重复 embedding 相似度 > 0.95，且结论一致 合并，保留更权威来源（期刊影响因子更高/被引更多），新句子标记为 duplicate_of
🟡 补充 相似度 0.8~0.95，且不同角度/不同实验条件 挂到同一 EvidenceCard，作为补充证据，增加证据多样性
🟢 支持 结论一致 + 独立来源（不同论文/不同实验） 增加 EvidenceCard 的证据强度（support_count++），作为独立验证
🩷 反驳 结论相反（LLM判断语义对立） 标记冲突（conflict_flag），触发人工/LLM复核，生成时同时呈现双方观点
🔵 更新 新结论取代旧结论（时间更新/方法更优/样本更大） 旧句子标记 deprecated，新句子标记 supersedes，生成时默认用最新有效证据
  • 规则兜底（快速判定）：相似度 > 0.95 → 直接判重复；同 paper_id → 不判关系；同 sentence_id → 跳过
  • LLM深度判定（0.8~0.95区间）：用 Ollama Qwen2.5 判断"补充/支持/反驳/更新"，输入：新句子 + 旧句子 + 上下文，输出：关系类型 + 置信度 + 理由
  • 置信度计算：confidence = 0.5×相似度 + 0.3×LLM置信度 + 0.2×来源权威度（期刊影响因子归一化）
  • 批量处理：所有 candidate_pairs 批量送 LLM，减少调用次数，控制成本
规则兜底 (相似度阈值) LLM深度判定 (Qwen2.5) 5种关系类型 置信度 = 相似度+LLM+权威度 批量LLM调用
（待实现：sentence_relation_classifier.py）

5
EvidenceCard 增量维护 — append / create / flag 冲突
待实现
📥 输入
sentence_relations[]（新句子与旧句子的关系）
→
📤 输出
更新后的 EvidenceCard 集合（append/create/flag/deprecated）
  • 属于已有 EvidenceCard → append：如果新句子的关系是"补充"或"支持"，且旧句子已属于某个 EvidenceCard，则将新句子追加到该 EvidenceCard 的 supporting_sentences 列表，更新 evidence_strength
  • 新主题 → create：如果新句子与所有旧句子相似度都 < 0.8，或关系判定为"新发现"，则创建新的 EvidenceCard，包含新句子作为初始证据
  • 冲突 → flag：如果关系是"反驳"，在相关 EvidenceCard 上标记 conflict_flag，记录冲突句子ID，生成时同时呈现双方观点并标注"存在争议"
  • 更新 → deprecated：如果关系是"更新"，旧 EvidenceCard 标记 deprecated_status = "superseded"，记录 superseded_by = 新 EvidenceCard ID
  • 重复 → merge：如果关系是"重复"，不创建新 EvidenceCard，将新句子标记为 duplicate_of，引用时指向已有 EvidenceCard
  • EvidenceCard 字段增强：增加 version、source_paper_ids[]、support_count、conflict_flags[]、deprecated_status、superseded_by、last_updated
append (补充/支持) create (新主题) flag (反驳/冲突) deprecated (更新/取代) merge (重复) EvidenceCard 版本管理
（待实现：evidence_card_incremental_manager.py） services/review/models.py (EvidenceCard 增强)

大纲挂载 — 新 EvidenceCard 按主题挂到大纲对应章节
部分实现（按大纲搜索分配已有）
📥 输入
新增/更新的 EvidenceCard 集合 + 已有大纲结构（章节+关键词）
→
📤 输出
更新后的大纲（每章节的 assigned_evidence_ids 更新）+ 可能的新章节建议
  • 主题匹配：对每个新 EvidenceCard，用其核心关键词（LLM提取或从句子中TF-IDF）与大纲各章节的关键词做匹配，找到最相关的章节
  • 向量匹配：用 EvidenceCard 的代表句子 embedding 与各章节的"章节向量"（该章节所有已分配证据的平均向量）做相似度计算
  • 分配到章节：将 EvidenceCard ID 追加到最相关章节的 assigned_evidence_ids 列表，更新章节的证据覆盖度
  • 找不到对应章节 → 建议新增：如果新 EvidenceCard 与所有章节的相似度都 < 阈值（0.6），提示用户"是否需要新增大纲节点？"，并给出建议的章节标题
  • 冲突证据特殊处理：标记 conflict_flag 的 EvidenceCard 同时挂到相关章节，生成时标注"存在争议"
  • deprecated 证据处理：标记 deprecated 的 EvidenceCard 从 assigned_evidence_ids 中移除（但保留在历史记录中）
关键词匹配 (TF-IDF) 章节向量匹配 (平均embedding) assigned_evidence_ids 更新 新章节建议 (相似度<0.6) 冲突证据标注
services/review/review_generator.py (search_and_assign_papers) services/review/outline_store.py

版本标记 — 每个句子/EvidenceCard 带 version 和 source
待实现
📥 输入
所有新增/更新的句子和 EvidenceCard
→
📤 输出
带版本标记的数据（version / source_paper_id / superseded_by / last_updated）
  • 句子版本：每个 sentence 记录 version（来自 paper 的 version）、source_paper_id、last_updated（论文更新时间）
  • EvidenceCard 版本：每个 EvidenceCard 记录 version（每次修改递增）、source_paper_ids[]（所有贡献论文）、created_time、last_updated
  • 取代关系：被取代的句子/EvidenceCard 记录 superseded_by = 新ID，新记录记录 supersedes = 旧ID，形成版本链
  • 不删除旧版本：旧数据不物理删除，只标记 deprecated_status = "superseded"，保留可追溯性
  • 生成时默认用最新：综述生成时默认过滤掉 deprecated 的证据，只使用最新有效证据；用户可选择"包含历史版本"查看
  • 版本差异对比：支持查看同一个 EvidenceCard 的版本历史，对比不同版本的证据变化（哪些论文新增/哪些被取代）
version 字段 source_paper_id 溯源 superseded_by 版本链 不删除只标记 (软删除) 默认用最新有效证据

影响范围评估 + 局部重算 — 只重算受影响部分，不全局重跑
待实现（性能优化关键）
📥 输入
新增/更新的 EvidenceCard + 大纲结构
→
📤 输出
受影响的章节列表 + 只重算这些章节的综述内容
  • 识别受影响章节：根据 EvidenceCard 挂载的章节，找出所有 assigned_evidence_ids 发生变化的章节（新增/删除/更新证据）
  • 传播影响：如果某章节证据变化，可能影响相邻章节的上下文（渐进式上下文注入用了前章摘要），标记相邻章节为"可能受影响"
  • 局部重算：只重新生成受影响章节的综述内容，未受影响章节直接复用上次生成结果，不全局重跑
  • 引用编号更新：局部重算后，更新全文的引用编号（[1][2]...），确保参考文献列表与文内引用对应
  • 变更日志：记录本次增量更新影响了哪些章节、新增了哪些证据、哪些证据被取代，生成"更新摘要"供用户查看
  • 性能对比：全局重算 vs 局部重算的耗时对比，展示增量更新的性能收益
受影响章节识别 相邻章节传播 局部重算 (不全局重跑) 引用编号更新 变更日志

💡 增量更新的 4 大核心设计原则

① 不重建，只追加 + 标记
旧数据不动，新数据挂上去。冲突用标记，不用删除。向量库用 collection.add 增量追加，不全量重建。
② 关系判定用 LLM + 规则
纯向量相似度不够，要 LLM 判断"支持/反驳/补充"。规则兜底：同 paper_id 不重复，同 sentence_id 不重复，相似度>0.95直接判重复。
③ EvidenceCard 是增量单位
不是论文，不是句子，而是 EvidenceCard。新论文进来，最终要落到 EvidenceCard 的增删改。句子是 EvidenceCard 的组成部分。
④ 增量要有"影响范围"评估
新证据进来，可能影响哪些章节、哪些结论？只重算受影响的部分，不全局重跑。性能优化的关键。
一句话：增量更新的本质，不是"加新论文"，而是"让新句子和旧句子建立关系，并更新 EvidenceCard"。

# 开发流程规范：架构即代码

> 日期：2026-11-03  
> 状态：**默认开发规则**（已写入 `.dsh_rules` 规则 0、AGENTS.md、CONTRIBUTING）  
> 真理源：`ARCHITECTURE.json`  
> 工具：`scripts/validate_arch.py`、`scripts/scaffold_from_arch.py`

## 1. 铁律

```text
1. 新增 / 修改 / 删除路由，先输出拟修改 JSON + 原因
2. 等人类明确回复“批准修改”
3. 收到批准后才写 ARCHITECTURE.json
4. 立刻运行 validate_arch.py
5. 校验通过后，才写路由和业务逻辑
6. 写完后再次运行 validate_arch.py
```

违反这条规则，视为架构漂移，不进入评审。

测试失败若因代码与 JSON 契约不一致：

```text
改 Python 适配 JSON
禁止反向改 JSON 参数来跑通测试
```

## 2. 为什么需要 planned 状态

新路由在 JSON 里存在、但 Python 还没写时，校验器不能把它当成“缺失路由”。

因此新节点必须：

```json
{
  "rule": "/api/foo/<int:item_id>",
  "endpoint": "foo.get_item",
  "methods": ["GET"],
  "status": "planned",
  "codegen": {
    "id": "foo_get_item",
    "blueprint": "foo",
    "function": "get_item",
    "mcp_server": "search_server",
    "mcp_tool": "get_foo_item",
    "description": "Return one foo item.",
    "parameters": [
      {"name": "item_id", "in": "path", "type": "int"},
      {"name": "verbose", "in": "query", "type": "bool", "default": false}
    ]
  }
}
```

状态流转：

```text
planned
  -> scaffold
  -> 实现并注册
  -> implemented（删除 status 或写 implemented）
  -> validate 通过
```

`validate_arch.py` 对 `planned` 只给 warning，不报错；对 implemented 路由做严格检查。

## 3. 标准操作

### 3.1 新增路由

```text
1. 在对话框输出拟修改 JSON 代码块 + 原因
   等待人类回复“批准修改”
   未收到批准前，JSON 和 Python 都不得改

2. 编辑 ARCHITECTURE.json
   - rule / endpoint / methods
   - status=planned
   - codegen 块

3. 运行
   python scripts/validate_arch.py

4. 生成骨架
   python scripts/scaffold_from_arch.py --node foo_get_item

5. 把 generated/foo_get_item/route.py 合入 routes/
   把 mcp_tool.py 合入 mcp_server/
   实现 handler 与 tool

6. 在 api_server.py 注册 blueprint

7. 把 JSON 的 status 改为 implemented
   （或删除 status 字段）

8. 再次运行
   python scripts/validate_arch.py

9. 跑对应测试
```

### 3.2 修改路由

```text
1. 输出拟修改 JSON + 原因，等待“批准修改”
2. 批准后改 JSON 的 rule / methods / endpoint
3. validate（此时旧代码会报 wild route 或 missing route）
4. 改 Python
5. validate 通过
```

### 3.3 删除路由

```text
1. 输出拟删除 JSON 节点 + 原因，等待“批准修改”
2. 批准后从 JSON 删除节点
3. validate 会报 wild route
4. 删除 Python 路由与 blueprint 注册
5. validate 通过
```

## 4. 校验器规则

`scripts/validate_arch.py` 检查：

```text
JSON route + method 集合 == Flask url_map 集合
JSON endpoint 函数存在
路径变量 <id> 必须在 handler 签名中
JSON parameters 声明的参数必须在 handler 签名中
重复 route+method 报错
status=planned 允许暂不实现
```

当前基线：

```text
json_routes   202
app_routes    202
OK
```

这里的 202 是 **route + method** 对，不是 URL 数量。

## 5. 生成器规则

`scripts/scaffold_from_arch.py`：

```text
只接受 status=planned
只接受带 codegen.id 的节点
输出到 generated/<id>/
不修改 api_server.py
不修改已有 routes/*.py
不修改 mcp_server/*.py
```

输出：

```text
generated/<id>/route.py
generated/<id>/mcp_tool.py
generated/<id>/README.md
```

生成器不会自动注册 blueprint，也不会自动插入 MCP 工具；这是故意的，避免脚本改坏生产入口。

## 6. MCP 约束

```text
MCP 是薄转发层
不 import services/*
不 import api_server
只通过 _forward._call 调 Flask 路由
```

生成器按这个约束生成：

```python
@mcp.tool(description="...")
def get_foo_item(item_id: int, verbose: bool = False) -> str:
    return _call("GET", f"/api/foo/{item_id}", {"verbose": verbose})
```

## 7. 例外

允许先写 Python 的情况只有：

```text
纯内部函数，不新增路由
没有 HTTP 入口
不改变 JSON 的 API 面
```

即使如此，也不能新增“野路由”。

## 8. 当前边界

```text
JSON 已有 204 route+method（开启 ingest-tracking 后 210）
validate_arch 已通过
scaffold 只生成骨架，不自动注册
参数校验目前覆盖 path 变量和显式 parameters
查询参数/请求体语义仍由 handler 自己负责
```

## 9. 失败处理

```text
validate 失败：
  先修 JSON 或 Python
  不允许用 --skip 绕过
  不允许临时注释校验

scaffold 失败：
  检查 codegen.id 是否唯一
  检查 status 是否为 planned
  检查 rule / methods

合并前：
  python scripts/validate_arch.py
  python -m unittest discover -s tests -p "test_*.py"
```

## 10. 全自动施工闭环（默认）

收到需求后默认自主推进，不逐步询问：

```text
1. 改 ARCHITECTURE.json
2. validate_arch.py
3. 写代码 / 生成骨架
4. 全量测试
5. 失败 -> 读日志 -> 修复 -> 重跑，直到 100% 通过
6. 写 Worklog
7. 提交分支 + 创建 PR（Pending Review）
8. 等待“批准合并”
```

必须停下来问的例外：

```text
- 无法解决的循环报错（同一错误 2 次以上）
- 核心鉴权逻辑（auth / tenancy / 权限判定）
- 不可逆的生产数据操作
- 研究裁决（claim / 证据 / 语料取舍）
- >300 行净变更的重大重构（只标记，不自动合并）
```

## 11. PR 审批策略

```text
创建后       Pending Review
等待人类     批准合并
收到批准后   merge
未收到批准   不得 merge / squash / rebase
```

只有精确回复 **“批准合并”** 才算授权；“合并”“可以”“LGTM”“CI 通过”都不算。

PR 描述必须包含：

```text
- 修改模块
- 业务逻辑变化
- 测试通过率
- 风险提示（外部 API / 数据写入 / 权限变化）
- 净变更行数
```

## 12. Worklog

路径：

```text
worklogs/YYYY-MM-DD-<topic>.md
```

必须包含：

```text
1. 需求
2. ARCHITECTURE.json 变化
3. 修改文件
4. 业务逻辑变化
5. validate_arch 结果
6. 测试命令与通过率
7. 风险 / 外部 API
8. 未完成项
```

## 13. 重大重构阈值

```text
净变更 <= 300 行    正常 PR
净变更 >  300 行    标题加 [LARGE]
                    描述顶部高亮“重大重构，需要专门评审”
                    不得自动合并
```

测试数量以当前套件实际结果为准，不硬编码 735 等历史数字。

## 14. ARCHITECTURE.json 物理拦截

已配置：

```text
.githooks/pre-commit   staged JSON 检查 + JSON 解析
.githooks/commit-msg   commit message 必须含 [APPROVED_BY_HUMAN]
```

为什么是两个钩子：

```text
Git 的 pre-commit 运行时还没有当前 commit message
所以“按提交信息阻断”必须放在 commit-msg
```

安装：

```powershell
git config core.hooksPath .githooks
```

测试：

```text
pre-commit  -> 发现 JSON staged，提示需要标签
commit-msg  -> 没有标签 -> exit 1；有标签 -> 放行
```

演示：

```text
git commit -m "arch: add foo route"
commit-msg: ... does not contain [APPROVED_BY_HUMAN]
exit 1

git commit -m "arch: add foo route [APPROVED_BY_HUMAN]"
[master ...] arch: add foo route [APPROVED_BY_HUMAN]
```

注意：

```text
git commit --no-verify 仍可绕过
钩子是防误操作，不是服务器端强制
```

## 15. 标准授权指令

修改 JSON：

```text
批准修改
```

合并 PR：

```text
批准合并
```

两个指令不能混用：

```text
“批准修改”只授权改 JSON
“批准合并”只授权 merge
```

## 16. 云端断服时的离线降级

当云端 API 断服，系统降级到本地 Ollama（如 qwen2.5:7b）时：

```text
禁止写代码
禁止修改 ARCHITECTURE.json
禁止重构路由
禁止执行 schema / migration
禁止创建或合并代码 PR
```

本地模型只允许：

```text
简单文本摘要
意图识别
闲聊问答
```

用户要求写代码时，直接拒答：

```text
当前处于离线降级模式，无法进行代码重构，请等待云端恢复。
```

理由：

```text
本地小模型不具备稳定的代码施工能力
断服期间改代码/JSON 会绕过 validate 与人工审批
恢复后难以判断哪一版是可信基线
```

## 17. 单机开发态测试标准

当前是单机台式机开发环境，不是生产服务器。

开发态必须做：

```text
python scripts/validate_arch.py
受影响模块单测
全量 unittest（当前 824 项，约 1 分钟）
改动路径 smoke test
Worklog + Pending Review PR
```

生产态再补：

```text
50/100 并发压测与 P95
异地备份、失败告警、恢复演练
30 天无回退观察
核心路径真实 PostgreSQL 集成测试
P6 SQLite 归档
```

边界：

```text
功能正确性、数据安全不能降
并发/容量/异地/高可用不阻塞当前开发
```

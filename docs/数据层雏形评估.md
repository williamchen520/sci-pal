# 数据层雏形评估

> 日期：2026-11-08  
> 对象：`scipal_v2` 与生产主库 `scipal_bench`  
> 结论：**已有正确的结构雏形，但尚未成为主架构数据层**

---


## 3. scipal_v2 的结构

### 3.1 documents

```text
document_id
paper_id
source_type       pdf / xml
source_path
sha256
parser
parser_version
imported_at
```

约束：

```text
PRIMARY KEY (document_id)
UNIQUE (paper_id, source_type, sha256)
FOREIGN KEY (paper_id) REFERENCES papers(paper_id) ON DELETE CASCADE
CHECK source_type IN ('xml','pdf')
```

评价：

```text
方向正确
但 source_type 只有 pdf/xml，MD 未支持
library_id / workspace_id 不在 documents 上
```

### 3.2 source_nodes

```text
node_id
document_id
paper_id
parent_node_id
node_type
source_path
source_order
native_json
created_at
```

约束：

```text
PRIMARY KEY (node_id)
FOREIGN KEY (document_id) REFERENCES documents(document_id) ON DELETE CASCADE
FOREIGN KEY (paper_id) REFERENCES papers(paper_id) ON DELETE CASCADE
FOREIGN KEY (parent_node_id) REFERENCES source_nodes(node_id)
```

节点量：

| node_type | 数量 |
|---|---:|
| sentence | 653,831 |
| paragraph | 136,240 |
| section | 59,972 |
| figure | 11,688 |
| table | 4,770 |
| paper | 2,903 |
| page | 1,374 |

评价：

```text
这是公共树的核心
native_json 是格式扩展入口
source_path 保存 XML XPath / PDF 路径
```

### 3.3 格式扩展

```text
pdf_pages
  document_id / paper_id / page_no / width / height / text / layout_json

pdf_blocks
  block_id / document_id / paper_id / page_no / bbox
  block_type / text / parent_block_id / source_order
```

XML 目前主要靠：

```text
source_nodes.native_json
```

没有独立的 `xml_*` 扩展表。ML/表格信息仍能保留，但查询不如 PDF 扩展直接。

### 3.4 公共派生表

```text
sections
paragraphs
sentences
figures
tables
```

都带：

```text
source_node_id
source_type
page / bbox
coordinate_source
```

这证明“公共树 + 格式坐标”的契约是可行的。

## 6. 关键缺口

| 缺口 | 严重度 | 说明 |
|---|---|---|
| 无 `work_id` | 高 | PDF 和 XML 无法聚成同一篇论文 |
| 无 `catalog/libraries` | 高 | 无法表达主库/租户库/来源库 |
| 无 `library_id` | 高 | 所有数据在同一命名空间 |
| 无联邦查询 | 高 | v2 没有接任何检索 |
| 无向量索引 | 高 | v2 只有 FTS，没有 embeddings |
| 无租户隔离 | 高 | 全部 `ws_default` |
| `source_type` 仅 pdf/xml | 中 | MD 不能入库 |
| `papers` 按 paper_id 覆盖 | 高 | 同一 paper 两种格式会互相覆盖 |
| `documents` 无版本/状态 | 中 | 只有 parser_version/imported_at |
| 398 篇没有 document | 低 | 元数据记录，可接受 |
| `native_json` 无 GIN 索引 | 低 | 目前不按 JSON 查询 |
| `SentenceFTS` 未接入 | 中 | 有 v2 代码，但应用未用 |

### 6.1 最危险的问题：paper_id 兼任 work 和 document

现在：

```text
papers.paper_id = 主键
documents.paper_id -> papers.paper_id
```

PDF 导入时会：

```sql
DELETE FROM papers WHERE paper_id = %s;
INSERT INTO papers ...
```

如果同一篇论文先导入 XML，再导入 PDF：

```text
papers 行被 PDF 覆盖
documents 留下两个
source_nodes 留下两棵树
公共派生表可能只剩一套
```

这不是联邦，而是**覆盖**。

所以第一步不是加索引，而是拆出：

```text
work_id
document_id
```

### 6.2 没有 library 维度

`documents` 没有：

```text
library_id
workspace_id
```

所有数据只能在一个隐式库里。  
要做主库/用户库/来源库，必须先有 library 注册表。

## 7. 目标契约

建议提升为以下五层：

```text
library
  library_id
  name
  scope          main / tenant
  owner_workspace
  source_type    pdf / xml / md / mixed
  schema_name
  status

work
  work_id
  primary_doi
  title
  year

document
  document_id
  work_id
  library_id
  source_type
  source_path
  sha256
  parser
  parser_version
  imported_at

node
  node_id
  document_id
  parent_node_id
  node_type
  source_path
  source_order
  native_json

extension
  pdf_pages / pdf_blocks
  xml_* / md_*
```

关系：

```text
library 1 ── n document
work    1 ── n document
document 1 ── n node
node    1 ── n extension
```

唯一性：

```text
work_id       全局稳定
document_id   每个格式版本唯一
node_id       每个 document 内唯一
```

## 8. 提升路径

### P0：只加契约，不动数据

```text
1. 新增 libraries 表
2. 新增 works 表
3. documents 增加 work_id / library_id
4. source_nodes 保持不动
5. 主库注册为 library_main
```

不迁移 10k 数据，不删除任何表。

### P1：主库回填

```text
papers 10,102
  -> works 10,102
  -> documents（按 filename / parse_engine 推断 pdf/xml）
  -> library_main
```

原则：

```text
不重新解析
不复制段落树
只在现有 papers/paragraphs 上建立 document 视图
```

### P2：新入库双写

```text
新 PDF/XML
  -> documents + source_nodes
  -> 兼容写 papers/paragraphs
```

旧表作为兼容视图，逐步退场。

### P3：联邦检索

```text
FederatedRetriever
  -> main library
  -> v2 pilot library
  -> RRF
  -> work_id 去重
```

### P4：租户库

```text
schema-per-workspace
主库只读角色
users 只能写自己的 library
```

### P5：MCP scope

```text
library_scope = own / federated / main
```

默认 `own`。

## 9. 建议

```text
不要把 scipal_v2 直接当生产库
不要全量重导 10k
不要先做联邦检索
```

先做：

```text
works + libraries + documents.work_id/library_id
```

这是最小改动、最大收益。

一句话：

```text
v2 证明了“树和格式扩展”可行
主库需要补的是“work / library / federation”三件事
```
